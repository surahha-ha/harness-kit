# 결정 질문 — 2단계에서 하나씩 묻는다

질문마다 **1단계 근거(파일:행)** 를 먼저 보이고, 선택지와 각 선택의 결과를 함께 제시한다. 사용자가 답하지 않은 칸은 내가 고르지 않는다 — `null` + 「미확정」 주석으로 두고 보고에 적는다.

아래 순서대로 묻는다. 앞 답이 뒤 질문의 선택지를 바꾼다.

## D1. 설치 위치 — 현 트리인가 worktree 인가

- 근거: 0단계의 미커밋 변경(특히 `.claude/settings.json`·`.gitignore`·`CLAUDE.md`)·살아 있는 다른 세션·stash.
- 선택지
  - **현 트리** — 미커밋 변경이 설치 대상 파일에 없고 다른 세션이 없을 때.
  - **worktree** — `git worktree add -b <설치 브랜치> <경로> <기준 커밋>`. 다른 세션의 미커밋 settings 와 섞이지 않는다. 대신 나중에 병합이 필요하고, 그 병합은 PITFALLS §5 의 기계 대조를 거친다.
- 결과가 들어가는 곳: 이후 모든 단계의 작업 경로, 9단계 브랜치 조건.

## D2. 공유 자원 — 무엇이 공유이고, deny 인가 ask 인가

- 판별 질문: **"이 대상을 나 말고 누가 동시에 쓰나?"** 호스트 이름이 아니라 연결이 최종적으로 닿는 곳으로 판별한다.
- 근거: 기본 프로파일의 datasource, 시작 스크립트의 환경변수, 테스트 코드의 하드코딩 접속, CI 설정.
- 선택지
  - **ask**(`dangerGuard.shared`) — 승인된 쓰기는 에이전트가 실행할 수 있다. 사람이 직접 치지 않아도 되므로 접속 정보가 대화에 덜 남는다.
  - **deny** — 에이전트는 절대 실행하지 않는다. 승인된 작업도 사람이 직접 쳐야 한다.
- `targetPattern` 은 그 공유 호스트(설치처 config 안에만), `writePattern` 은 쓰기 구문. 조회는 막지 않는다.
- 함께 보고할 것: 하드코딩된 자격증명을 찾았으면 위치만 알리고 **교체(rotate) 여부는 사용자 판단**으로 넘긴다.

## D3. `commands.unitTest` 의 범위 — 외부 자원이 필요한 테스트를 넣는가

- 판별 질문: **"이 명령의 종료코드만 보고 통과/실패를 판정할 수 있나?"** 파이프는 넣지 않는다.
- 근거: 1단계의 테스트 분류(순수 단위 / 로컬 컨테이너 통합 / 공유 자원 직결).
- 선택지
  - **통합 포함** — 실행 전 컨테이너를 띄워야 하고 없으면 무관한 레드가 난다. config 주석과 CLAUDE.md 에 선행 조건과 「실행 전 대상 환경 확인」을 적는다.
  - **통합 제외** — 이름 관습이나 태그로 거를 수 있을 때만. 목록을 박아 거르면 새 테스트가 빠진다.
- **공유 자원에 직접 붙는 테스트는 어느 쪽이든 뺀다.** 빌드 파일을 고치지 않고 빼는 수단(빌드 도구의 init script·명령줄 필터 등)이 있는지 보고, 소스에서 지우거나 비활성화하는 것은 레포 정책 변경이라 따로 묻는다.
- 모노레포: 최상위 `commands.unitTest` 는 `cd <하위> && <명령>` 꼴, kit `project.commands.be/fe` 는 **cd 없이**(kit 이 `sides.*.root` 로 들어간 뒤 붙인다).

## D4. `dangerGuard.deny` — 2~3개만

- 판별 질문: **"실행 후 5분 안에 원상복구할 수단이 있나?"** 둘째 축: **"결과가 틀려도 조용히 다음 작업의 입력이 되는가?"**(출력 파이프로 종료코드를 잃는 것 등)
- 후보는 1단계 근거에서 나온 것만 보인다: 공유 자원 직결 테스트를 부르는 전체 테스트 명령, 빌드·테스트 출력 파이프, 볼륨·데이터 삭제 명령.
- 규칙마다 `id`·`why`·`recover` 를 같이 정한다. `recover` 에는 막힌 사람이 칠 **통과하는 명령**을 적는다.
- `ask` 후보(정상 절차인데 무언가 사라지는 것 — `git reset --hard`·`git clean -f` 등)도 같은 자리에서 묻는다.
- `probe.token` 은 우연히 등장하지 않을 고유 문자열로 짓는다.

## D5. 커밋 정책 — 레포 규칙과 `project.git.*` 를 맞춘다

- 근거: 레포 `CLAUDE.md` 의 커밋·push·trailer 규칙, `git log` 의 메시지 관례, 보호 브랜치.
- 물을 것
  - 이번 설치 커밋을 **실행**할지, 메시지만 건넬지(레포 규칙이 「커밋하지 않음」이면 특히).
  - `project.git.commitExecution` — `'auto'` | `'message-only'` 둘뿐이다. 레포 규칙과 같은 뜻의 값으로.
  - `project.git.push` — `'auto'` | `'ask'` | `'never'`. `coAuthor` — trailer 허용 여부(레포 규칙).
  - `reviewThreshold` — `{ files, lines }` 또는 미정(`null`, 이 경우 kit save 의 diff 리뷰 게이트를 건너뛴다는 것을 알린다).

## D6. 플러그인 겹침 — 같은 역할 스킬이 두 벌 뜨는가

- 근거: `~/.claude/settings.json` 과 레포 settings 의 `enabledPlugins`, 각 플러그인의 스킬·에이전트 이름.
- 같은 역할의 스킬·에이전트가 harness-kit 과 다른 플러그인에서 함께 뜨면 어느 쪽이 트리거될지 모호해진다.
- 선택지
  - **이 레포에서 끈다 — 커밋되는 settings.json** 에 `"<이름>@<마켓>": false`. 팀 전체에 같은 상태. 대신 개인이 쓰는 플러그인 이름이 커밋된다.
  - **이 레포에서 끈다 — `settings.local.json`**. 개인 설정으로 남는다. 대신 worktree 마다 다시 해야 한다.
  - **그대로 둔다**.
- 키는 설치 기록·사용자 settings 에 적힌 `<이름>@<마켓>` 과 **문자 그대로** 같아야 한다.

## D7. 나머지 슬롯 — 근거가 있을 때만 채운다

- `testFirst` — 기본은 `enabled: false`. 레포에 이미 test-first 훅이 있으면 `auditOnStop` 만 켤지 묻는다. 경계표(scopes)가 없으면 켜지 않는다.
- `qualityCycle.evidence` — 관찰만 한다. 넣을지, 넣으면 어떤 유형인지 묻는다.
- `drift.mirrors` — 레포 안의 사본↔원본 짝이 있을 때만. 개인 PC 의 절대경로를 가리키는 미러는 커밋되는 config 에 넣지 않는다.
- `project.memory.slugs` — PC 마다 다른 값이다. 넣을지 묻는다.
- `approvals.*` — 사람 이름 대신 역할을 적는다(예: 「레포 소유자 — 실행 직전 대화로 승인」).
