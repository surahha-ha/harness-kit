# 실전 함정 — 단계별

각 단계를 시작할 때 같은 번호 절을 읽는다. 설치·재현 시험·걷어내기 시험에서 터진 것이다.

## §0 사전 확인

- **워킹트리를 커밋본으로 단정하지 않는다.** 설치가 커밋되지 않은 채 작업본에만 있는 트리가 있었다. 그 트리는 걷어 낸 뒤 HEAD 와 같아져 커밋할 것이 없다 — 7단계에서 「커밋 경로 0개」가 정상이다.
- **같은 트리의 다른 세션이 settings.json 을 고치는 중일 수 있다.** 걷어내기는 키 단위라 남의 변경을 지우지 않지만, 경로 지정 커밋은 파일 단위라 그 변경까지 커밋에 싣는다.
- **중단된 설치를 걷어내기로 다루지 않는다.** harness-install 체크포인트가 남은 트리는 example 그대로인 config·반쯤 들어간 settings 가 섞여 있다. 그 정리는 harness-install 0단계의 「초기화」가 체크포인트를 기준으로 한다.

## §1 후보 뽑기

- **영수증이 없으면 「설치 뒤 손댔는가」를 가릴 수 없다.** 상태가 `unknown` 인 후보는 지우기 전에 사용자가 직접 확인한다. 하네스 원본의 그 SHA 판(config 머리 줄)과 대조하면 `.harness/` 는 가릴 수 있지만, 이 스킬은 원본을 받지 않는다.
- **영수증 없는 설치에서 8단계의 문서 고침은 후보가 아니다.** 커맨드·에이전트 문서의 테스트 명령을 보조 파일을 쓰는 꼴로 바꾼 줄이 레포 곳곳에 있었다. 영수증 없이 「설치가 바꾼 줄」을 가리는 근거는 HEAD 와의 diff 뿐인데, 그것으로 되돌리면 §4 의 사고와 같다 → 참조 목록으로 보고만 하고, 그 줄들이 가리키는 보조 파일은 남김을 권한다.
- **sha256 은 줄끝을 LF 로 맞춘 뒤 계산한다.** autocrlf 트리에서는 같은 커밋을 받아도 PC 마다 CRLF·LF 가 달라, 바이트 해시로는 모든 파일이 「손댐」으로 뜬다.
- **설정 슬롯 값은 지우기 전에 읽는다.** `project.git.commitExecution` 은 config 안에 있다 — config 를 지운 뒤에는 커밋 정책을 알 길이 없다(1단계 스크립트가 체크포인트에 적어 둔다).

## §2 결정 질문

- **이 스킬도 harness-kit 안에 있다.** 「끔」을 고르면 다음 세션부터 이 레포에서 harness-install 이 뜨지 않아, 재설치하려던 사용자가 막힌다 → 목적을 먼저 묻고 플러그인 키는 맨 마지막에 묻는다.
- **런타임 산출물을 남기면서 `.gitignore` 줄을 지우면** 로그가 미추적 파일로 떠 다음 커밋에 섞일 수 있다 → 런타임 질문을 항목보다 먼저 묻는다.
- **false 키를 지우면 그 플러그인이 다시 켜진다.** 설치가 겹침 때문에 끈 플러그인이다 — 같은 이름의 스킬이 두 벌 뜨는 상태로 돌아간다는 것을 선택지에 적는다.

## §3 백업

- **백업은 한 번만 뜬다.** 걷어내기가 끊긴 뒤 백업을 다시 뜨면 반쯤 지운 상태가 「원본」이 된다. 스크립트는 체크포인트에 백업이 있으면 다시 뜨지 않는다.
- **worktree 의 `git-path` 는 그 worktree 와 함께 지워진다.** `git worktree remove` 를 하면 백업도 사라진다. 증거 데이터(런타임 산출물)는 그래서 `git-common-dir` 아래에 따로 둔다. 백업을 오래 둘 거면 보고 뒤 레포 밖으로 옮기라고 안내한다.

## §4 걷어내기

- **`git restore` 로 걷어 냈다가 하네스와 무관한 파일까지 되돌렸다.** 하네스를 작업본에서 걷어 내려고 git 의 되돌리기로 HEAD 판에 맞췄는데, 하네스와 상관없는 파일·변경까지 함께 되돌아갔다. `git restore`·`git checkout -- <파일>`·커밋 되돌리기는 파일·커밋 단위라 「넣은 것만」을 지키지 못한다 → 블록·줄·치환·키 단위로만 지운다.
- **settings.json 을 parse → stringify 로 다시 쓰면 서식이 바뀐다.** 들여쓰기·키 순서·한 줄로 적은 객체가 바뀌어 하네스와 무관한 diff 가 생긴다. 스크립트는 지울 member 의 바이트 범위만 잘라 낸다(앞 member 끝부터 그 member 끝까지).
- **같은 이벤트 키가 두 번 생긴 settings.json 에서 훅이 조용히 사라졌다.** 병합이 이벤트 키를 따로 더해 한 객체에 같은 키가 둘이 됐고, `JSON.parse` 는 뒤쪽만 남겼다. 걷어내기도 파싱 결과만 보면 앞쪽 키의 훅을 못 본다 → 6단계가 중복 키를 세고, 하네스가 아닌 훅을 이벤트별로 백업과 기계 대조한다. 중복 키가 이미 있으면 걷어내기 전에 멈추고 보고한다.
- **같은 그룹·같은 이벤트의 다른 도구 훅을 건드리지 않는다.** 하네스 훅이 다른 도구 훅과 한 이벤트 배열에 함께 있었다(설치가 기존 배열에 그룹을 더한 경우). 훅 하나를 지울 때 그룹이 비면 그룹을, 이벤트가 비면 이벤트 키를 지우고, 그 밖은 바이트 그대로 둔다.
- **아직 살아 있는 가드가 걷어내기 명령을 막는다.** 재귀 삭제(`rm -rf` 류)는 흔히 ask·deny 규칙이다. 파일 삭제는 스크립트 안에서 하고, 셸 인자에는 경로·id·답만 넘긴다.
- **`.harness/` 를 지운 뒤 이 세션의 훅이 도구 호출마다 오류를 낸다.** 세션이 시작할 때 올라온 훅 명령이 없어진 파일을 부른다. 종료코드 1 이라 막지는 않는다. 새 세션에서 사라진다 — 사용자에게 미리 알린다.

## §5 플러그인 키

- **`claude plugin uninstall --scope project` 도 settings.json 을 통째로 다시 쓴다.** 설치 때 `install` 이 키 순서를 바꾸고 다른 도구의 배열 값을 지운 적이 있다. 실행 전 백업 → 실행 → 대조·복원이 한 묶음이다.
- **사용자 범위에서도 켜 둔 PC 는 project 키를 지워도 플러그인이 뜬다.** 「끔」의 효과가 PC 마다 다르다는 것을 보고에 적는다.

## §6 검증

- **status 는 M 인데 diff 는 비어 있는 파일이 있었다.** 설치가 CRLF 체크아웃 파일을 LF 로 다시 썼고, 걷어내기는 바이트를 보존해 LF 가 남았다. 내용은 HEAD 와 같다 — 커밋 대상이 아니고 「줄끝만 다름」으로 보고한다. 줄끝을 맞추려고 `git checkout` 하지 않는다(§4).
- **남은 참조는 실패가 아니다.** 후보 밖 문서가 보조 파일 이름을 가리키는 줄은 의도적으로 남긴 것이다. 목록으로 보고하고, 고칠지는 사용자가 정한다.

## §7 커밋

- **`auto` 정책이어도 묻는다.** 커밋 확인을 띄우던 것은 하네스 가드였다 — 걷어 낸 뒤에는 확인 없이 커밋된다.
- **지운 파일도 경로로 넘긴다.** `git commit -- <경로>` 는 추적 중인 파일의 삭제를 경로로 받는다. `git add -A` 로 모으면 후보 밖 변경까지 들어간다.
- 브랜치·toplevel 조건은 커밋과 같은 명령에 건다.

## §8 재설치

- **같은 세션에서 바로 harness-install 을 돌리지 않는다.** 옛 훅·옛 `CLAUDE.md` 규칙이 세션에 남아 있어 0단계 관찰이 틀어지고, 설치 중 옛 가드가 오류를 낸다 → uninstall → 새 세션 → install.
- 영수증을 남긴 채(항목 일부를 남김) 재설치하면 harness-install 0단계가 그 트리를 「끝난 설치」로 본다. 재설치가 목적이면 게이트 항목은 모두 지운다.
