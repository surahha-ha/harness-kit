# QA Cycle — 구현부터 결과 리포트까지 단일 표준 흐름

이 skill 은 "구현→검증→e2e→리포트(퍼센트)" 흐름의 표준이다. 사용자가 이 흐름을 요청하면 **모든 단계를 빠뜨리지 않고** 동일한 품질로 제공한다.

이 skill 은 레포의 테스트 규약(`docs.testGuide`)과 정렬된다. 그 규약을 더 구체적이고 실행 가능한 단계로 확장한다. 둘이 어긋나면 레포 문서가 우선한다.

## 프로필 — 프로젝트 고유값을 읽는 곳

이 스킬은 프로젝트 고유값을 본문에 갖지 않는다. 레포 루트 `harness.config.mjs` 의 `project` 블록에서 읽는다(슬롯 정의는 harness-kit README 「프로젝트 프로필」).

- 읽는 순서: 현재 레포 config → `project.pairOwner` 가 가리키는 주 레포 config.
- 이 스킬이 읽는 슬롯: `commands.be.*` · `commands.fe.*` · `e2e.modeSwitch` · `sides.fe.uiTipsDoc` · `docs.testGuide` · `docs.uiUxRules` · `risk.sharedDbSuites` · `memory.policy`
- **값이 없으면 지어내지 않는다.**
  - 파일이 없거나 슬롯 키가 없으면 그 자리에서 멈추고 사용자에게 묻는다.
  - 테스트 명령을 흔한 형태로 추측해 돌리지 않는다.
  - `null` 은 "해당 없음으로 판단됨"이다. 그 단계를 건너뛰고 리포트에 적는다.

## 트리거 신호

다음 중 하나 이상이 보이면 이 skill 을 즉시 활성화한다:
- "전체 사이클로 / QA 사이클 / qa-cycle 진행"
- "동일한 방식으로 디버깅 / 이 흐름으로 진행해줘"
- "구현 + 검증 + e2e + 리포트"
- "퍼센트 / 완성도 알려줘"
- "리포트 형식으로 정리"
- 이번 프로젝트에서 한 번이라도 이 흐름이 진행됐고 사용자가 같은 결을 요청

## 5 단계 표준

### Stage 0 — 명세 확정 (사용자 컨펌)

작업이 **product 결정**을 내포하면 코드부터 만들지 말고 명세부터 확정한다.

- **트러블슈팅 원칙 적용**: 가설 최소 3개 제시, 단정 금지
- 가능한 매핑/룰을 표로 미리 보여주고 사용자가 ✓/✗ 짚을 수 있게
- "Q1~Q4" 식 짧은 옵션 카드로 한 번에 묶어 묻기 (반복 질문 금지)
- 모호한 부분은 "이게 맞나요?" 정밀 확인. 추측으로 진행 금지

**산출물**: 확정된 명세표 + 사용자 답변 반영

### Stage 1 — 구현

- **단일 source of truth** 추출 우선 (예: utility / dictionary class)
- 작은 diff 원칙 — 기존 호출처는 wrapper / alias 위임으로 압축
- 변경 범위가 frontend + backend + DB 에 걸치면 단계 분리를 고려한다.
  - 이번 PR 에 모든 걸 다 넣지 않는다.
- 새 필드 추가 시 폼 초기값 / DB schema / 내보내기 사전까지 일관 갱신

**산출물**: 변경 파일 표 (파일 / 변경 요약)

### Stage 2 — 검증 (단위/회귀)

- 핵심 로직은 **순수 함수로 추출**해 단위 테스트 가능하게 설계
- 변경된 모듈 + 영향 범위 모듈의 기존 테스트 모두 회귀 (`commands.be.testOne` · `commands.fe.testOne` 으로 좁혀서)
- `risk.sharedDbSuites` 에 걸린 스위트는 대상 환경을 확인받은 뒤에만 돌린다
- **결과는 숫자로**: `15/15 PASS`, `30/30 PASS` 형식

**산출물**: 회귀 결과 표 + PASS/FAIL 카운트

### Stage 3 — e2e 테스트

- spec 두 트랙으로 분리:
  - **트랙 A**: 순수 함수/유틸 직접 import 검증
    - 토큰/서버가 필요 없다. 빠른 회귀다.
  - **트랙 B**: UI flow
    - mock/실서버 전환 방식과 그 SSOT 는 `e2e.modeSwitch` 가 가리키는 곳을 따른다.
    - mock 이 기본이면 토큰·백엔드 없이 개발 서버만으로 돈다.
- 페이지에 같은 라벨이 여러 곳 있으면 **컨테이너로 query 한정** (`page.locator('<폼 루트>').getByLabel(...)`)
- UI 라이브러리 컴포넌트 래퍼가 `<input>` 을 감싸 **label-for 연결이 끊기는** 경우가 흔하다.
  - `getByLabel` 이 안 잡히면 래퍼 컨테이너로 좁힌 뒤 `locator('input')` 으로 내려간다.
  - 라이브러리별 팁은 `sides.fe.uiTipsDoc` 에 있다.
- 팝업/모달처럼 오버레이를 띄우는 컴포넌트는 다른 요소가 클릭을 가로채므로 `{ force: true }` 또는 오버레이 렌더 대기 후 클릭
- 토큰이 없다고 UI 트랙을 skip 하지 않는다.
  - mock 모드가 있으면 그대로 돈다.
  - skip 하고 "e2e N/N PASS" 를 보고하면 거짓 그린이다.
- npx 충돌 회피: `./node_modules/.bin/playwright test ...` 직접 호출

#### 실패 판정 — 측정 규율

e2e 스위트는 결정론적이지 않다. **같은 커밋을 다시 돌려도 실패 건수와 목록이 달라진다.**
한 테스트가 실패하면 그 덤프를 쓰느라 context teardown 이 timeout 을 넘기 때문이다. 그러면 무관한 후속 테스트까지 연쇄로 죽는다.
레포에 규율 문서가 있으면 `docs.testGuide` 가 SSOT 이고, 요지는 넷이다.

1. **단일 실행 1회로 baseline 을 확정하지 않는다.**
   - 같은 조건에서 반복 측정하거나, 의심 스펙만 단일 파일로 교차 확인한다.
2. **판정 대상과 baseline 은 같은 조건에서 잰다.**
   - 전체 실행분과 단일 파일 실행분을 비교하지 않는다.
3. **e2e 실행 중에는 다른 명령을 병행하지 않는다.**
   - 부하가 곧 teardown timeout 이라 결과가 바뀐다.
4. **실패가 광범위하면 회귀보다 환경·연쇄를 먼저 의심한다.**
   - retry 로 통과하는 건 flaky 로 분류한다.
   - flaky 는 "즉시 픽스" 대상에서 뺀다.

> 이 규율이 없어 **정상 변경을 회귀로 오판해 되돌렸다가** 재판정에서 뒤집힌 적이 있다. 허수 기준선은 멀쩡한 코드를 지운다.

**산출물**: e2e 결과 (예: `17/17 PASS`)

### Stage 3.5 — UI/UX 정합성 검증

기능 동작이 OK여도 시각/레이아웃이 깨지면 사용자가 알아챈다. e2e 직후 또는 PR 리뷰 때 다음 체크리스트로 점검한다. 화면을 새로 만들거나 흐름을 바꾼 작업이면 `harness-kit:ui-ux-guide` 의 CHECKLIST 가 우선한다. 레포 규범은 `docs.uiUxRules` 다.

#### 동적 콘텐츠 컨테이너 일관성
- 라벨/값 2열 표에는 **라벨 폭을 고정**한다.
  - 긴 value(경로/URL/전화번호/JSON 직렬화 텍스트)가 컨테이너를 가로로 늘리지 않게 한다.
- **CSS 패턴** (필수): 표는 `table-layout: fixed; width: 100%`, 값 셀은 `word-break: break-all; white-space: pre-wrap; overflow-wrap: anywhere`
- 사이드 패널 / 모달 / 드로어 안에서는 동적 콘텐츠 폭을 제한한다.
  - 부모가 `min-width: 0` 이 아니면 flex 자식이 안 줄어든다.
- 그리드의 긴 텍스트 컬럼은 툴팁 표시 또는 `min-width` + word-break

#### 라벨/표기 일관성
- 한 의미가 여러 곳에서 같은 한국어 라벨로 표시되는지 (`기동 계정` vs `기동계정` 같은 공백 차이 없음)
- 코드값 → 라벨 변환(`categoryLabel`, `statusLabel`, `purposeLabel` 등)은 모든 표시 지점에서 적용한다.
  - detail / list / form / export 모두 같은 변환을 쓴다.
- 빈 값 표시 일관 — `—` (em dash) 권장. `-` / `""` / `null 그대로` 혼용 금지
- 한국어 라벨이 표준. 영어 라벨은 약어/축어 (`URL`, `OS`, `CPU`) 한정

#### 폼 입력 정합성
- 숫자 입력에 **min/max/소수자리를 모두 명시** — clamping 동작이 정의돼야 한다
- 텍스트 입력은 `maxlength` + 남은 글자수 표시로 자릿수 제한을 시각화
- placeholder 는 **예시값** (예: `"GIT"`, `"백업 서버"`). 실명/실제 데이터 노출 금지 (`"홍길동"` 같은)
- 자동 생성/계산 필드는 `readonly` + label 에 `(자동)` 명시

#### 점검 도구
- 사용자가 detail 화면 캡쳐 보내면 받은 그대로 라벨/순서/줄바꿈 검토 후 픽스
- 같은 패턴(예: 라벨 폭 미고정) 이 다른 페이지에도 있는지 grep:
  - `grep -rn "<문제 컴포넌트/클래스>" <sides.fe.root>/src/`
  - 누락된 곳 발견 시 동일 패턴 적용

#### 웹 표준 / 접근성 (WCAG 2.1 AA 기준)
- **시맨틱 HTML** — `<button>` 을 `<div onclick>` 으로 대체 금지. 헤딩(h1~h6) 계층 일관
- **ARIA 라벨** — 아이콘 only 버튼은 `aria-label` 필수.
  - UI 라이브러리 컴포넌트는 보통 자동 처리된다. 커스텀 컨트롤은 명시한다.
- **키보드 네비게이션** — `Tab` 으로 모든 인터랙티브 요소를 순회할 수 있다.
  - 모달 진입 시 포커스 트랩을 건다. 탈출 시 트리거 버튼으로 포커스를 되돌린다.
- **포커스 표시** — `:focus-visible` outline 유지 (제거 금지). 라이브러리 기본 스타일이 outline 을 제거했다면 커스텀
- **색상 대비** — 본문 텍스트 4.5:1, 큰 텍스트(18px+) 3:1. 색상에만 의존하지 않음 (예: 빨강+아이콘 / 초록+체크)
- **이미지 alt** — 의미 있는 이미지는 alt, 장식은 `alt=""` 빈 값

#### 반응형 / 다양한 해상도 (운영 도구는 데스크탑 우선이지만)
- **최소 지원 폭**: 1280px (운영 데스크탑 기본). 레포 규범이 다르게 정했으면 그것을 따른다
- 사이드 패널 / 메인 영역 비율은 작은 모니터(1366x768)에서도 깨지지 않도록
- 가로 스크롤 페이지 레벨 발생 금지 — 컴포넌트 내부 스크롤로 격리
- 터치 디바이스 감안 시 클릭 영역 최소 **44x44px** (Apple HIG / Material guideline)

#### 최신 UX 트렌드 (2024~2026)
- **Skeleton loader** — spinner 보다 페이지 형태 미리 보여주는 skeleton 권장 (체감 속도)
- **빈 상태 (empty state)** — "데이터가 없습니다" 만 적지 말고 다음 액션을 제안한다.
  - 예: "+ 새 항목 등록" 버튼
- **점진적 노출 (progressive disclosure)** — 폼 너무 길면 collapse 섹션, 고급 옵션은 접어두기
- **마이크로 인터랙션** — 호버 / 포커스 / 클릭 / 로딩에 부드러운 transition (150~250ms)
- **다크 모드** — `prefers-color-scheme` 미지원이라도 향후 도입 가능하게 색상 변수화 (CSS variables)
- **확인 다이얼로그는 destructive 에만** — 일반 저장/취소엔 불필요. 삭제/덮어쓰기/되돌릴 수 없는 작업만
- **토스트 알림** — 5초 자동 사라짐 + 중요 액션은 사용자 dismiss 필요
- **8px grid system** — margin/padding 은 4/8/12/16/24/32 같은 8 의 배수 기준으로 일관

#### 사용자 피드백 / 상태 명확성
- **로딩 상태** — 1초 이상 걸리는 액션은 명시적 로딩 (버튼 spinner / skeleton / 진행률)
- **에러 메시지** — 구체적으로 쓰고 해결 방법을 제시한다.
  - 좋은 예: "저장 실패 — 이름이 중복됩니다. 다른 이름을 입력해주세요"
  - 나쁜 예: "오류"
- **성공 메시지** — 즉시 토스트 + 화면 자동 갱신
- **저장 안 된 변경** — 페이지 이탈 시 `beforeunload` / 확인 모달로 경고
- **중복 클릭 방지** — 저장 버튼은 첫 클릭 직후 `disabled` + `loading`

#### 데이터 표시 일관성
- **빈 셀** — `—` (em dash, U+2014) 로 통일. `-` / `""` / `null` 노출 금지
- **숫자** — 정렬 right-align + 천 단위 구분자 + 단위 명시 ("16 GB" / "100 GB" 모두 일관)
- **날짜** — 한국어 환경 기본 `YYYY-MM-DD` 또는 `YYYY-MM-DD HH:mm`. 타임존 명시 필요 시 표기
- **표 정렬** — 가능한 컬럼은 sortable 표시 (정렬 가능 컬럼은 헤더에 화살표)
- **긴 텍스트** — 표는 overflow 툴팁, detail 은 `word-break + pre-wrap` (위 동적 콘텐츠 항목)

#### 작업 분리 원칙
- UI 정합성 fix 는 보통 CSS-only — frontend hot reload 로 즉시 반영
- e2e 영향 거의 없음 (라벨/값 텍스트 검증은 그대로). 별도 e2e 추가 불필요
- 단 자릿수/clamping/사용자 입력 검증 같은 동작 변경은 e2e B 트랙에 추가
- a11y 자동 검증 도구: `axe-core` / `playwright-axe`. 미도입이면 도입은 별도 백로그

#### 점검 시 우선순위
1. **즉시 차단 (운영 영향)** — 가로 확장, 버튼 안 보임, 폼 저장 실패, 키보드 진입 불가
2. **시각적 일관성** — 라벨/빈값/코드 변환, 라벨 폭 고정, 8px grid
3. **체감 품질** — skeleton, 빈 상태, 마이크로 인터랙션
4. **a11y 확장** — ARIA, 키보드, 색상 대비

각 PR 에서 1~2 는 필수, 3~4 는 권장 (도메인별 백로그 등록).

**산출물**: UI/UX 정합성 체크리스트 결과 — 발견한 위반과 적용한 fix + 백로그 등록 항목

### Stage 4 — 결과 리포트 (필수 항목)

작업 완료 시 **모든 항목을 빠뜨리지 않고** 정리:

#### 4.1 변경 요약
| 파일 | 종류 | 변경 |
|---|---|---|
파일/신규/리팩터/삭제 별 표

#### 4.2 검증 결과
- 단위 테스트 N/N PASS
- e2e A 트랙 N/N + B 트랙 N/N
- 라이브 회귀 (있으면) 결과
- **확인 근거** — 위 수치와 확인 주장(통과 · 없음 · 일치 등)마다 한 줄을 단다.
  - 꼴: `주장 · 근거(돌린 명령, 또는 대조한 파일:줄·커밋) · 입력(본 데이터·계정·브랜치·조합) · 결과(종료코드와 결과 줄)`
  - 못 채운 주장은 검증 결과에서 뺀다. 4.2 끝에 「미확인: 주장 — 이유」로 따로 적는다.
  - 빈 출력은 같은 실행의 종료코드 0 을 함께 봤을 때만 「없음」이다.
  - 규칙과 미확인 이유의 라벨은 `harness-kit:coordinator` §2 「확인 근거 칸」을 따른다.

#### 4.3 추가 발견사항 (작업 중 마주친 것)
- **버그**: 기존 코드의 잠재적/실제 버그
- **개선**: UX/성능/안전성 개선 여지
- **필요 기능**: 사용자 시나리오상 빠진 기능
- **업계 표준**: 운영에서 보통 어떻게 처리하는지

#### 4.4 완성도 퍼센트
정량 평가:
- **70-79%**: 핵심 동작 확인, 회귀 테스트 부족
- **80-89%**: 핵심 + 회귀 OK, 엣지 케이스/UX 보완 여지
- **90-94%**: 운영 가능 수준, 안전망 제거 후속 필요
- **95-100%**: 운영 즉시 가능, 모든 안전망 검증 완료

#### 4.5 95~100% 로 올리려면 (개선 항목)
현재 점수 기준 누락된 것 구체적으로 제시:
- 예: "현재 90% — 95%+ 가려면 (a) 가져오기 미리보기 UI 분리 (b) 사용자 임의 키 정리 정책 결정 (c) 상세 화면의 임시 별칭 매핑 안전망 제거"

#### 4.6 후속 백로그 등록
다음 세션에서 이어가기 위한 백로그를 `memory.policy` 가 정한 자리에 명시 등록한다. 슬롯이 없으면 어디에 남길지 사용자에게 묻는다.
백로그는 우선순위 순서로 적는다(B1, B2, B3...).

## 단계 간 호출 규칙

- **Stage 0 → 1**: 사용자 컨펌 받고 구현 시작. 컨펌 없이 구현 금지.
- **Stage 1 → 2**: 구현 직후 단위 테스트 즉시 (코드만 던져두고 테스트 미루지 말 것)
- **Stage 2 → 3**: 단위 PASS 확인 후 e2e. 단위 실패 상태로 e2e 진입 금지
- **Stage 3 → 4**: e2e 실패는 먼저 **회귀 / flaky / spec 불일치**로 분류한다.
  - 분류 기준은 Stage 3 「실패 판정 — 측정 규율」이다.
  - 회귀·spec 불일치는 픽스한 후 4단계로 간다.
  - flaky 는 flaky 로 명시해 리포트한다.
  - 분류 없이 "실패=회귀"로 코드를 되돌리지 않는다.
  - 실패를 무시하고 리포트하지 않는다.

## 중간 보고 빈도

- 각 Stage 완료 시 짧게 보고 ("2단계 30/30 PASS, 3단계 진입")
- Auto mode 활성 시 보고만 하고 즉시 다음 단계
- 사용자 결정 필요 지점 (Stage 0, 4.5 의 추가 개선 진행 여부) 만 차단

## Anti-pattern (이 skill 활성 시 절대 금지)

- 명세 컨펌 없이 추측으로 구현 → "Q1~Q4" 카드로 먼저 정렬
- 단위 테스트 생략하고 e2e 만 → 단위 → e2e 순서 강제
- e2e fail 을 "다음에 픽스" 로 미룸 → fail 은 즉시 픽스 또는 명시적 skip.
  - 단 **분류가 먼저**다. flaky 를 코드 결함으로 확정해 정상 변경을 되돌리지 않는다.
- "잘 됐어요" 단순 보고 → 항상 4 단계 형식 리포트. 확인 주장마다 확인 근거(4.2)를 단다
- 한 PR 에 여러 도메인 섞기 → 단계 분리 (예: 폼 합성 / 가져오기 미리보기 UI)
