# 결정 질문 D1~D12 · 현황판

0단계에서 하나씩 정한다. 항목마다 「먼저 볼 곳」에서 코드로 답을 찾는다. 코드로 못 정한 것만 묻는다.
질문할 때는 권장안과 이유를 함께 낸다. 선택지 표는 질문 창이 아니라 그 앞 응답 본문에 둔다.
「전송 부록이 답한다」가 붙은 항목은 SKILL.md 「전송 방식 부록」의 T 질문이 먼저다.
결과는 이 파일 끝 「결정 기록 양식」으로 레포 문서에 남긴다.

## D1. 전송과 송신 결과

- 먼저 볼 곳: 전송 클라이언트 설정 · 송신 호출부 · 수신 설정 · 전송 판
- 전송 부록이 답한다: T3(송신 확인) · T8(기록 지점 자리)
- 송신 결과(`sendResult`)는 아래 세 질문으로 정한다. 셋은 따로 답한다.
  1. **송신 확인 신호가 있는가**(브로커 확인 · 전송 응답 · 완료 콜백).
     - 있으면: 그 신호에서 `SENT`·`FAILED` 를 정한다. 그 이벤트의 `at` 은 확인 시각이다. 확인이 늦으면 B 의 응답이 A→B 요청보다 먼저 보인다. 화면은 먼저 온 응답 창(D11)으로 짝짓는다(RULES.md §2). 확인 지연을 알면 적는다. 창 길이의 근거가 된다.
     - 없으면: 송신 호출이 예외 없이 끝나면 `SENT` 다. 「도착 확인 없음」을 계약에 적는다.
  2. **거절을 알리는 코드를 받는가**(권한·대상 없음 등). 받으면 `REJECTED` 를 쓴다. 받지 못하면 `REJECTED` 는 생기지 않는다고 계약에 적는다.
  3. **끊긴 동안 송신을 쌓아 두는 버퍼(오프라인 큐·재시도 버퍼)가 있는가.**
     - 없으면: 끊긴 상태의 송신은 즉시 `NOT_SENT` 다.
     - 있으면: `NOT_SENT` 를 쓰지 않는다. `NOT_SENT` 는 "보내지 않았고 앞으로도 보내지 않는다"일 때만 쓴다.
       - 확인 신호가 있으면 신호를 기다려 1건(`SENT`·`FAILED`)만 낸다. 권장이다.
       - 확인 신호가 없으면 쌓은 순간 `QUEUED` 1건을 낸다. 화면은 대기로 판정한다(RULES.md §4).
       - 버퍼가 상한·재시작으로 버려질 수 있으면 그 결과는 끝내 오지 않는다. 가이드 「한계」에 적는다.
     - 한 송신에 이벤트는 1건이다. 쌓을 때와 나갈 때 1건씩 내면 같은 키의 요청이 둘로 보여 앞 것이 시간 초과가 된다.
- **응답이 송신 호출의 결과로 오는 전송**(동기 요청·응답, 예: HTTP 호출): 그 순간 요청 이벤트를 먼저, 응답 이벤트를 다음에 낸다. 먼저 온 응답이 생기지 않는다. D11 「먼저 온 응답 창」은 「해당 없음」이다.
- **확인 신호를 받는 데 본 처리 클라이언트 설정 변경이 들면**(T3 ①, 예: 비동기 송신의 성공 통지를 켜는 옵션) 사용자 승인을 받는다. 그 설정은 본 처리 메모리·처리량을 바꾼다. 승인이 없으면 질문 1 은 「확인 신호 없음」으로 답한다.
- **런타임 유형**(SKILL.md 2단계 2): 판정 기준은 「큐를 비우는 일을 본 처리와 다른 실행 단위로 넘길 수 있는가」다. 스레드형(콜백이 클라이언트 스레드·스레드풀에서 옴) · 경량 스레드형(예: Go goroutine, 콜백이 본 처리 핸들러 안에서 와도 채널로 넘긴다) · 이벤트 루프형(본 처리와 같은 루프라 넘길 수 없다) 중 하나다.
- 기록할 것: 전송·클라이언트·판, 세 질문의 답, 송신 결과 값 목록, 동기 응답 흐름 여부, 런타임 유형

## D2. 메시지 종류 — 요청·응답 판별

- 먼저 볼 곳: 채널 상수·빌더, 수신 설정, 봉투 DTO
- 전송 부록이 답한다: T1(채널 체계)
- 정할 것
  - 요청과 응답을 무엇으로 가르나: 채널 이름 · 봉투 칸 · 전송 헤더 중 하나다.
  - 테넌트를 어디서 뽑나. 뽑지 못하면 그 메시지는 버린다. D5 가 「단일 범위」면 뽑지 않는다.
  - 응답이 가는 끝점(요청한 쪽)을 어디서 읽나.
  - **요청·응답이 아닌 메시지**(알림·상태 이벤트 등)를 어떻게 하나.

| 선택지 | 바뀌는 것 |
| - | - |
| (a) BE 가 버린다 | 계약의 `kind` 는 요청·응답 둘뿐이다. 가이드 「한계」에 "요청·응답이 아닌 메시지는 보이지 않는다"를 적는다 |
| (b) `kind: "EVENT"` 로 보낸다 | FE 는 중립 행으로 보인다. 짝·처리 결과·대기 판정과 지표에서 뺀다. 송신 배지는 받는다. 규칙은 RULES.md 각 절의 `EVENT` 행 |

- 권장: 그런 메시지가 실제로 있으면 (b), 없으면 (a).
- 요청·응답이 하나도 없는 시스템(이벤트만 오감)이면 (b) 다. 짝 관련 절(RULES.md §2·§3·§5·§6, UI.md §5 요청·응답 탭)은 「해당 없음 — 이유」로 적는다.
- 어느 쪽이든 FE 파서가 계약 밖 값을 **조용히** 버리지 않게 한다. 기준 구현에서 `kind: null` 이 와서 파서가 말없이 버렸다.
- 기록할 것: 판별 규칙, 테넌트·응답 끝점 위치, 요청·응답이 아닌 메시지의 처리

## D3. 상관 키

- 먼저 볼 곳: 요청·응답 봉투 DTO, 명세의 공통 메시지 규격
- 전송 부록이 답한다: T2(상관 키 위치) · T7(중복·재전송)
- 정할 것
  - 키 이름과 위치. 예: 봉투 최상위 `requestId`, 또는 전송이 주는 상관 칸.
  - 재전송 때 같은 키를 다시 쓰는가. 쓰면 같은 키의 요청이 여러 번 보인다. 짝 규칙(RULES.md §2)이 이를 처리한다.
  - 응답 봉투에 `action` 이 있는가. 있으면 계약에 싣고, 없으면 null 이다(CONTRACT.md §3). 화면이 응답 행의 action 을 채우는 순서는 RULES.md §4-1 `action` 칸 하나다.
  - 응답의 처리 결과 칸. 예: `success` boolean. 없거나 boolean 이 아니면 결과 없음이다.
  - 키가 없는 메시지는 짝을 찾지 않는다.
- 기록할 것: 키·위치, 재사용 여부, 응답 결과 칸

## D4. 상대 ID 출처 · 자기 송신 판별 · 패널 묶음 키

- 먼저 볼 곳: 요청·응답 봉투 DTO, 응답 채널 빌더, 클라이언트 접속 설정(ID 생성), 전송 판
- 전송 부록이 답한다: T4(상대 ID) · T5(자기 송신 되돌림)
- 전송 메시지에 보낸 끝점의 ID 가 늘 실리지는 않는다. 모니터가 읽을 수 있는 곳만 쓴다.
- 정할 것
  1. **흐름마다 상대 ID 를 어디서 읽나.** 봉투 최상위 · 봉투 `data` 안 · 채널 이름 조각 · 전송 메타데이터(헤더·속성) · 연결 인증 정보(끝점이 A 에 직접 붙는 전송) · 없음 중에서 고른다. 결과를 CONTRACT.md §5 표에 채운다.
     - 전송 메타데이터는 본 처리가 이미 싣는 경우만 쓴다. 모니터 때문에 싣기 시작하면 본 처리 송신이 바뀐다.
  2. **자기 송신 되돌림을 어떻게 가리나.** A 가 보내는 채널을 A 도 받으면 그 메시지가 A 로 돌아온다. 송신 기록이 이미 있으니 수신 기록에서 버린다.

| 방법 | 쓸 수 있을 때 | 주의 |
| - | - | - |
| (a) 봉투의 보낸 쪽 ID 가 A 의 것인가 | 봉투에 보낸 쪽 ID 가 있다 | 되돌림은 다른 A 인스턴스로 갈 수 있다. "이 인스턴스"가 아니라 "A 의 어느 인스턴스"인지로 가린다(접두 규칙 등) |
| (b) 보낸 상관 키를 TTL 집합에 기억 | 봉투에 ID 가 없다. 상관 키가 송신마다 유일하다 | TTL ≥ 응답 제한시간. 되돌림이 다른 인스턴스로 가면 그 인스턴스는 모른다. 인스턴스가 2대 이상이면 집합을 인스턴스 사이에 공유한다(기존 캐시 등) |
| (c) 전송 메타데이터의 보낸 쪽 표식 | 본 처리가 이미 싣는다 | 위 1 의 조건과 같다 |
| (d) 전송의 수신 옵션으로 막는다 | 전송 부록 T5 가 그런 옵션과 조건을 적었다 | 본 처리 수신 설정을 바꾸는 일이라 사용자 승인을 받는다 |
| (e) 해당 없음 | A 가 보내는 채널을 A 가 받지 않는다 | — |

  3. **패널을 묶을 키가 없을 때.** 패널 칸 키는 상대 ID 다(RULES.md §11).
     - 쌍 중 한쪽에만 있어도 그 키로 묶는다. 예: B→A 요청에 없어도 A→B 응답의 받는 쪽에 있으면 그 쌍은 묶인다.
     - 짝이 없는 행은 「ID 없음」 칸에 모인다.
     - 어느 흐름에서도 얻지 못하면 둘 중 하나를 고른다. 다른 묶음 키(예: `data` 의 단말 ID)를 정하거나, 패널 보기를 만들지 않는다.
     - 패널 보기를 만들지 않으면 보기는 2종이다. 캡처 `view-panel` 과 가이드 패널 설명을 뺀다.
- 권장: 봉투에 ID 가 있으면 (a). 없으면 (b).
- 기록할 것: 흐름별 출처 표, 되돌림 판별 방법, 패널 묶음 키(또는 패널 없음), A 인스턴스 ID 의 출처(호스트 이름·환경 변수 등)와 수명(재배포 때 바뀌나 — 바뀌면 접두 규칙과 칩 꼬리가 그 이름에서 서는지 본다)

## D5. 테넌트 범위와 인증 주체

- 먼저 볼 곳: 인증 필터, 현재 사용자 조회 유틸, 테넌트 해석 코드
- 정할 것
  - 인증 주체에서 테넌트를 어떻게 푸나. 외부 조회면 그 장애는 503 이다.
  - 누가 볼 수 있나(역할·권한). 권한이 없으면 FE 가드가 막고, BE 는 403 이다.
  - 한 사용자가 여러 테넌트를 가지면 어떻게 하나. 권장: 연결 때 한 테넌트로 정한다. 고르는 화면이 필요하면 별도 결정으로 미룬다.
  - 범위가 하나뿐인 시스템이면 「단일 범위」로 적는다. 권한 검사는 그대로 둔다.
- **요청 파라미터로 테넌트를 받지 않는다.** 받으면 다른 테넌트의 메시지를 열 수 있다.
- 기록할 것: 해석 경로, 권한, 장애 때 상태

## D6. PII 키 목록과 마스킹 방식

- 먼저 볼 곳: 기존 마스킹 유틸, 개인정보 필드 정의, 상대 시스템 명세 문서
- 정할 것
  - **상대가 보내는 payload 의 키 목록을 어디서 받나.** 명세 문서 · 스키마 · 실제 샘플 중 무엇인가.
  - A 가 보내는 payload 의 키 목록. 이것은 A 코드에서 뽑는다.
  - 마스킹 방식

| 선택지 | 안전 | 비용 |
| - | - | - |
| (a) 가릴 키 목록(목록 밖은 원문) | 상대가 모르는 키로 PII 를 실으면 원문이 나간다 | 화면이 읽기 쉽다 |
| (b) 보일 키 목록(목록 밖은 가림) | 새 키는 일단 가려진다 | 키를 추가할 때마다 목록을 고친다 |

- 권장: 상대 키 목록을 받았으면 (a) + 4단계 대조. 못 받았으면 (b), 또는 실고객 데이터가 흐르지 않는 환경에서만 켠다(D7).
- 키별 가림 방식과 큰 덩어리(서명·이미지·설문 원문)의 요약 대체를 정한다(MASKING.md).
- 키 이름 비교는 기본이 대소문자 무시다(MASKING.md §1). 바꾸면 이유를 적는다.
- 전송 메타데이터(T10: 메시지 키·헤더 등)를 화면에 올리면 그 키도 마스킹·대조 대상이다(MASKING.md §1·§4). 올리지 않으면 계약에서 `transportMeta` 를 뺀다(CONTRACT.md §3).
- 기록할 것: 키 목록 출처와 받은 날짜, 방식, 키별 규칙, 키 비교 방식, 가리지 않는 키와 이유, 전송 메타데이터를 올리는지

## D7. 켜는 환경

- 먼저 볼 곳: 환경별 설정 파일, 전송 전체 플래그, FE 빌드 모드 변수
- 정할 것: 환경별 표

| 환경 | 실고객 데이터가 흐르나 | 전송 전체 플래그 | 모니터 플래그 | 결과 |
| - | - | - | - | - |
| 로컬 | | | | |
| 개발 | | | | |
| 검증 | | | | |
| 운영 | 예 | | `false` | 꺼짐 |

- **게이트는 환경 이름이 아니라 「실고객 데이터가 흐르나」로 정한다.**
  - 그 칸이 「예」인 환경은 마스킹 키 대조(MASKING.md §4)가 끝나기 전에 모니터 플래그를 켜지 않는다.
  - 운영 복제 데이터를 쓰는 검증 환경, 실단말이 붙는 개발 환경도 「예」다. 모르면 「예」로 둔다.
- BE: 전송 전체 플래그(있으면)와 모니터 플래그가 **둘 다** 참일 때만 기록·팬아웃·엔드포인트가 생긴다. 꺼지면 404 다. 전송 전체 플래그가 없으면 그 칸은 「해당 없음」이다.
- FE: 운영 빌드면 진입 가드가 다른 화면으로 보낸다. 빌드 모드를 지정하지 않은 빌드가 운영인지 확인한다.
- 운영에서 켜려면 별도 승인을 받고 결정 기록에 남긴다. 그때 FE 가드 기준 변수도 함께 바꾼다. BE 플래그만 켜면 FE 가드가 계속 막는다.
- 기록할 것: 표, 플래그 이름, FE 가드 기준 변수

## D8. 브라우저 전달 수단

- 먼저 볼 곳: 이미 있는 실시간 스트림(SSE·WebSocket), 프록시 설정
- 이 결정은 서버 → 브라우저 구간이다. 시스템 사이의 전송(D1)과 다르다.

| 수단 | 장점 | 주의 |
| - | - | - |
| SSE(`EventSource`) | 브라우저 자동 재연결. 단방향으로 충분하다 | 헤더를 못 붙인다(쿠키만). 실패 응답의 상태·본문을 못 읽는다 → 닫힌 뒤 상태 확인 요청 |
| fetch 스트림 | 헤더 토큰을 붙인다. 상태를 읽는다 | 재연결·이벤트 파싱을 직접 만든다 |
| WebSocket | 양방향 | 모니터에는 과하다. 인증·프록시 설정이 따로 든다 |

- 권장: 이미 쓰는 수단. 없으면 SSE.
- 함께 정할 것: 이벤트 이름, 하트비트 주기(프록시 유휴 타임아웃보다 짧게), 서버 연결 타임아웃, 프록시 응답 버퍼링 끄기
- 기록할 것: 수단, 경로, 이벤트 이름, 하트비트·타임아웃 값

## D9. 인스턴스 간 팬아웃 · 다중 인스턴스 중복 수신

- 먼저 볼 곳: 이미 쓰는 pub/sub 버스(메시지 브로커·캐시 pub/sub 등), 다른 스트림의 팬아웃 구조
- 전송 부록이 답한다: T6(같은 메시지를 몇 대가 받나)
- 정할 것
  - **A 인스턴스가 2대 이상이면 팬아웃이 필요하다.** OUTBOUND 는 보낸 인스턴스에만 기록되고, 브라우저는 어느 인스턴스에 붙을지 모른다. 단일 인스턴스면 `해당 없음 — 이유`.
  - 버스 채널 이름. 버스 메시지는 `{테넌트, 이벤트}` 다.
  - **INBOUND 를 몇 대가 기록하나.** 채널마다 받는 A 인스턴스 수로 가른다. 한 대만 받으면(나눠 받는 수신 · 인스턴스 전용 채널) 받은 한 대가 기록하고 팬아웃한다. 모두 받으면 아래 (a)·(b) 중 고른다. 일부만 받으면 (b) 다.

| 선택지(여러 대가 같은 메시지를 받을 때) | 바뀌는 것 |
| - | - |
| (a) 그 INBOUND 는 버스에 싣지 않고 자기 연결에만 보낸다 | 브라우저마다 한 벌이다. 그 채널을 **모든** 인스턴스가 받을 때만 맞다. `receiverId` 는 브라우저가 붙은 인스턴스다 |
| (b) 그 INBOUND 를 기록할 인스턴스를 하나 정한다(설정값·리더 선출). 기록한 것은 팬아웃한다 | 그 인스턴스가 내려가면 그 INBOUND 가 보이지 않는다. 가이드 「한계」에 적는다 |

- 권장: 기존 스트림과 같은 버스·같은 구조를 쓴다. 채널과 연결 보관소는 분리한다. 한 프로젝트 안에서 채널마다 다를 수 있다.
- 권장(받는 대수별): 모든 인스턴스가 받는 채널은 (a), 일부만 받으면 (b), 한 대만 받으면 받은 한 대가 팬아웃한다. (b) 는 기록 인스턴스가 내려가면 유실되므로 (a) 가 맞는 곳에 쓰지 않는다.
- **버스 확인 항목.** 짝 규칙은 브라우저 수신 순서에 기댄다(RULES.md §2). 버스가 아래를 지키는지 확인하고 결정 기록에 적는다.
  - **순서:** 같은 테넌트 이벤트가 기록 순서대로 모든 인스턴스에 닿는가. 예: Kafka 를 버스로 쓰면 메시지 키 = 테넌트(같은 파티션). 키가 없거나 라운드로빈이면 A→B 응답이 B→A 요청보다 먼저 닿아 짝 없음·거짓 시간 초과가 된다. 지키지 못하면 RULES.md §2 의 전제가 깨진다. 가이드 「한계」에 적는다.
  - **모두 받기:** 모든 인스턴스가 받는가(브로드캐스트). 예: Kafka 는 인스턴스마다 다른 소비 그룹을 써야 한다. 같은 그룹이면 한 대만 받는다. 인스턴스가 바뀔 때 버려진 그룹이 쌓이는지도 본다.
  - **시작 위치:** 새로 붙은 인스턴스가 최신부터 받는가. 처음부터 받으면 지난 이벤트가 다시 흐른다.
  - **보존:** 버스가 이벤트를 보존하나. 보존하면 마스킹한 이벤트라도 이력 저장이 된다(이 스킬 범위 밖). 보존을 끄거나 가장 짧게 둔다.
- **확인 항목 — 요청과 응답의 `at` 을 같은 인스턴스가 찍는가.** 소요(RULES.md §6)는 두 `at` 이 같은 시계라는 전제에 기댄다. B→A 요청은 받은 인스턴스가 응답도 보내는지, A→B 요청은 보낸 인스턴스만 응답을 받는지 본다. 아니면 소요에 시계 차이가 섞인다. 시계 동기(NTP 등)를 확인하고 가이드 「한계」에 적는다. 응답 채널을 여러 대가 나눠 받으면 요청과 응답을 다른 인스턴스가 기록해, 버스에 싣는 순서도 정해지지 않는다(위 「순서」).
- 기록할 것: 버스, 채널 이름, 채널별 수신 방식과 받는 인스턴스 수, INBOUND 기록 규칙, `at` 같은 인스턴스 여부, 버스 확인 항목 넷의 답

## D10. 인증 갱신 방식

스트림은 앱 HTTP 클라이언트의 인증 갱신 경로 밖에 있다. 401 에 그냥 멈추면 인증 만료만으로 모니터가 선다.
먼저 앱의 인증 방식을 가른다.

| 선택지 | 맞는 인증 방식 | 바뀌는 것 |
| - | - | - |
| (a) 401 하나마다 앱 HTTP 클라이언트로 갱신을 1회 부르고 재연결 | 쿠키에 담은 토큰 + 갱신 엔드포인트 | 갱신이 실패하거나 아래 상한에 닿을 때만 멈추고 재로그인을 안내한다 |
| (b) fetch 스트림 + 헤더 토큰. 재연결 전에 토큰을 갱신 | 헤더 토큰 + 갱신 엔드포인트 | 스트림 구현을 직접 한다(D8) |
| (c) 갱신 없음. 401 이면 멈추고 재로그인 안내 | 서버 세션(httpOnly 세션 쿠키), 또는 갱신 엔드포인트가 없는 토큰 | 인증 수명보다 오래 켜 두면 멈춘다. 가이드 「한계」에 적는다 |

- 권장: 갱신 엔드포인트가 있으면 (a), 헤더 토큰만 쓰면 (b), 서버 세션이면 (c).
- **서버 세션이면 두 가지를 확인해 적는다.**
  - **rolling 연장:** 긴 연결은 연결을 여는 요청에서만 세션을 건드리는 경우가 많다. 그러면 화면을 켜 둔 동안 세션이 만료된다. 재연결 요청은 연장하고, 서버가 보내는 하트비트는 연장하지 않는다.
  - **열린 연결의 만료:** 세션이 만료돼도 열린 스트림은 계속 흐를 수 있다. 하트비트 때 세션을 다시 확인해 만료면 닫거나, 최대 연결 시간을 둔다.
- **갱신 횟수(a·b).** 401 하나에 갱신을 1회 부른다. 갱신이 실패하면 바로 멈춘다. 갱신이 성공했는데 또 401 이면 또 1회 부른다. 이어진 횟수가 상한(D11)에 닿으면 멈춘다. 연결이 열리면 0 으로 되돌린다. 판정 입력은 RULES.md §12 `classifyStreamProbe` 의 `refresh` 다.
- 기록할 것: 인증 방식, 선택지, 갱신 호출 경로, 상한, (서버 세션이면) rolling 여부·열린 연결 만료 처리

## D12. 화면 표기

- 정할 것
  - 시스템 표시 이름. 방향 라벨이 `{상대}→{우리}` · `{우리}→{상대}` 다. 상대가 둘 이상이면 상대마다 이름을 두고, 방향 라벨은 `{상대}` 자리에 「상대」 같은 묶음 이름을 쓴다.
  - 참여자 칩: 어느 쪽 ID 인지 가리는 규칙과 접두(예: `A-`·`B-`), 남길 꼬리 글자 수.
  - 모르는 ID 의 표기. 받는 끝점을 송신 때 특정할 수 없으면 그 사유를 전송 부록의 답(T4·T6)으로 고른다: 그 테넌트의 끝점이 모두 받음(예 라벨 「테넌트 전체」) · 끝점 중 한 곳이 나눠 받음(예 라벨 「나눠 받음」) · 그 밖은 「알 수 없음」. 칩 라벨은 측 + 괄호 사유(예: `B(테넌트 전체)`).
  - 칩 색. 기준 구현은 **역할색 2개**(A 쪽 한 색, B 쪽 한 색)다. 참여자마다 색을 주지 않는다(RULES.md §14).
  - 시각 라벨. 예: `{우리} 수신 시각` · `{우리} 송신 시각`.
- 기록할 것: 라벨 원문. 문구 상수 파일 위치

D1~D12 뒤에 묻는다. 현황판은 화면을 연 뒤 받은 메시지를 누적해 지표·추이·분포로 보이는 두 번째 화면이다(UI.md §14).

| 선택지 | 바뀌는 것 |
| - | - |
| (a) 만든다 | SKILL.md 3B단계를 한다. RULES.md §16·§17 과 `현황판` 행을 센다. 가이드 11절과 캡처 `board` 를 더한다. D11 의 현황판 값 셋을 정한다 |
| (b) 만들지 않는다 | 3B단계와 위 항목을 모두 건너뛴다 |

- 권장: 사용자가 누적 집계·추이(「오래 띄워 두고 이상이 생겼는지 본다」)를 원할 때만 (a). 모니터만으로 답이 되면 (b).
- 나중에 더할 수 있다. 수신부·판정을 모니터와 함께 쓰므로 모니터를 고치지 않고 더한다.
- 기록할 것: 있음 / 없음, 그 이유(사용자 답·날짜)
