# 스트림 이벤트 계약

BE 와 FE 가 함께 따르는 계약이다. 1단계에서 이 프로젝트 값으로 채워 레포 문서 한 곳에 둔다.
계약이 바뀌면 BE·FE 를 같은 변경에서 고친다. 예시 값은 모두 합성값이다. 필드 이름은 예시다. 바꾸면 이 문서 전체에서 함께 바꾼다.

## 1. 엔드포인트

| 항목 | 값 |
| - | - |
| 경로 | `GET {base}/monitor/stream` — 경로는 프로젝트가 정한다 |
| 응답 형식 | `text/event-stream`(D8 이 SSE 일 때) |
| 인증 | 필수. 테넌트는 인증 주체에서 연결 때 한 번 푼다 |
| 요청 파라미터 | 없다. 테넌트를 고르는 파라미터를 두지 않는다 |
| 하트비트 | D8 주기로 보낸다. SSE 주석 줄(예: `: hb`) 또는 FE 가 무시하는 이벤트(§2 `ping`) 중 하나다. 프레임워크가 주석 줄을 못 내면 이벤트로 낸다 |
| REST 호출 | 없다. 이력 조회가 없다 |

## 2. 이벤트

| 이름 | 횟수 | `data` |
| - | - | - |
| `connected` | 연결 직후 1회 | `{"tenantId": "…"}` — 이 연결에 묶인 테넌트. 화면 연결 상태에 보인다 |
| `message` | 메시지 1건마다 | 아래 필드표의 객체 |
| `ping` | 하트비트를 이벤트로 낼 때만, D8 주기 | `{}`. FE 는 처리하지 않는다. EventSource 는 핸들러를 달지 않으면 무시한다. fetch 스트림이면 파서가 건너뛴다 |

## 3. `message` 필드표

**모든 키가 늘 온다. 값이 없으면 `null` 이다.** 키를 빼지 않는다.

| 필드 | 형식 | 뜻 |
| - | - | - |
| `id` | string | 서버가 매긴 이벤트 ID(UUID). 전송의 메시지 ID 가 아니다 |
| `at` | string | ISO-8601, 밀리초·오프셋 포함. INBOUND = A 가 받은 시각, OUTBOUND = 송신 결과가 정해진 시각(D1 확인 신호가 있으면 그 시각). 그래서 A→B 요청의 `at` 이 그 응답의 `at` 보다 늦을 수 있다(RULES.md §2·§6) |
| `direction` | `"INBOUND"` \| `"OUTBOUND"` | B→A \| A→B |
| `kind` | `"REQUEST"` \| `"RESPONSE"` (+ D2(b)면 `"EVENT"`) | D2 규칙으로 판정 |
| `channel` | string | 실제 채널(토픽·큐·경로 등) |
| `senderId` | string \| null | 보낸 참여자. 판정은 §5 |
| `receiverId` | string \| null | 받을 참여자. 판정은 §5 |
| `correlationId` | string \| null | 상관 키(D3) |
| `action` | string \| null | 봉투의 action. 응답 봉투에 없으면 null(D3). 화면이 응답 행을 채우는 순서는 RULES.md §4-1 `action` 칸이다 |
| `success` | boolean \| null | 응답만. 그 밖은 null |
| `sendResult` | string \| null | OUTBOUND 만. §4 |
| `error` | string \| null | **송신 문제 사유만.** `sendResult` 가 `REJECTED`(거절 코드)·`FAILED`(예외 문자열)·`NOT_SENT`(보내지 않은 이유)일 때 싣는다. `SENT`·INBOUND 는 null. 처리 실패 사유는 payload 안에 있다 |
| `payload` | object \| array \| string | 마스킹한 본문. JSON 객체·배열로 읽지 못하면 사유 문구 문자열 |
| `transportMeta` | object \| null | **선택 칸**(T10). 화면에 올리기로 한 전송 메타데이터(예: `{"key": …, "partition": 3, "offset": 1042, "headers": {…}}`). 올리면 MASKING 규칙을 같이 적용한다. 올리지 않기로 했으면 이 칸을 계약에서 뺀다 |
| `sentAt` | string \| null | **선택 칸**(T12). 메시지에 실린 보낸 시각(ISO-8601). 전송이 싣지 않으면 이 칸을 계약에서 뺀다. 소요 계산에는 쓰지 않는다(RULES.md §6) |

- `kind` 를 판정하지 못한 메시지의 처리는 D2 결정을 따른다. `null` 을 보내지 않는다.
- 언어 기본 직렬화가 null 칸을 빼거나(예: Go `omitempty`) 시각의 밀리초 자릿수를 바꾸지(끝의 0 지움) 않는지 확인한다. 계약 픽스처에 밀리초가 0 인 시각을 하나 둔다.
- 브라우저로 보내지 않는 것: 원문 payload, 버스 메시지(§8) 전체. 브라우저에는 그 안의 `event` 만 간다.
- 테넌트는 `connected` 로 한 번 알린다. 그 연결 자신의 테넌트라 보여도 된다. `channel` 안의 테넌트 조각도 같은 테넌트다. 다른 테넌트의 값은 어느 칸에도 싣지 않는다.

## 4. 송신 결과 값(`sendResult`)

| 값 | 뜻 | 화면 결과 |
| - | - | - |
| `SENT` | 전송이 받았다(확인 신호 성공), 또는 확인 신호가 없는 송신이 예외 없이 끝났다 | 배지 없음. 결과는 처리 결과·대기 등으로 |
| `REJECTED` | 전송이 받고 거절했다(거절 코드) | 송신 거절 |
| `FAILED` | 확인이 실패했거나(미응답 등) 송신 요청을 만들지 못했다 | 송신 실패 |
| `NOT_SENT` | 연결이 없어 보내지 않았고, 앞으로도 보내지 않는다 | 송신 실패 |
| 그 밖의 문자열 | 예: `QUEUED` — 오프라인 버퍼에 쌓았고 확인 신호가 없다(D1) | 원문 그대로 중립 배지. 판정하지 않는다. 결과 필터 대상이 아니다 |

- 어느 값을 쓰는지는 D1 의 세 질문(확인 신호 · 거절 코드 · 오프라인 버퍼)이 정한다. 전송 부록 T3 이 출발점이다.
- 거절 코드를 받지 못하면 `REJECTED` 는 생기지 않는다. 오프라인 버퍼가 있으면 `NOT_SENT` 를 쓰지 않는다. 계약에 그렇게 적는다.
- `FAILED` 에는 "확인만 못 받은" 경우가 섞인다. 실제로는 도착했을 수 있다. 화면 설명에 적는다.

## 5. 참여자 ID 판정

봉투·채널·전송 메타데이터에서 **읽기만** 한다. 모니터 때문에 봉투·채널을 바꾸지 않는다.
표의 「상대 ID」는 D4 가 그 흐름에 정한 출처의 값이다. 출처가 없으면 null 이다.

| 흐름 | `senderId` | `receiverId` |
| - | - | - |
| B→A 요청 | 상대 ID | 받은 A 인스턴스의 ID |
| A→B 응답 | 이 A 인스턴스 | 응답이 가는 끝점(요청한 상대, D2) |
| A→B 요청 | 이 A 인스턴스 | 받는 끝점이 정해지면 그 ID. 송신 때 특정할 수 없으면(모두 받음 · 나눠 받음, T4) null |
| B→A 응답 | 상대 ID | 응답이 가는 끝점(요청한 A 인스턴스, D2) |
| `EVENT` | 수신: 상대 ID · 송신: 이 A 인스턴스 | 수신: 이 A 인스턴스 · 송신: 받는 끝점 또는 null |

- 상대 ID 출처가 없는 흐름은 보낸 쪽이 null 이다. 화면은 짝 상대 쪽 ID 로 묶는다(RULES.md §11).
- 판정 예(합성): 봉투에 ID 가 없고 응답 채널 이름의 한 조각에만 있으면, B→A 요청의 `senderId` 는 null 이다. 그 짝 A→B 응답의 `receiverId` 는 상대 끝점이다. 패널은 그 쌍을 그 끝점 칸에 묶는다.

## 6. 예시

B→A 요청(받음):

```json
{
  "id": "0b8e6a52-6f1d-4c2a-9a51-3d4c2b7e9f10",
  "at": "2026-01-15T10:00:01.234+09:00",
  "direction": "INBOUND",
  "kind": "REQUEST",
  "channel": "example.tenant-001.orders.request",
  "senderId": "b-node-7f2a",
  "receiverId": "svcA-app01",
  "correlationId": "req-7c1f",
  "action": "CREATE_ITEM",
  "success": null,
  "sendResult": null,
  "error": null,
  "payload": { "requestId": "req-7c1f", "action": "CREATE_ITEM", "data": { "name": "김*수", "phone": "010-****-5678" } }
}
```

A→B 요청(보내지 못함): 위와 같은 꼴이고 칸만 다르다. `direction: "OUTBOUND"` · `senderId: "svcA-app02"` · `receiverId: null` · `sendResult: "NOT_SENT"` · `error: "transport unavailable"`.

읽을 수 없는 본문: `"payload": "JSON 객체로 읽을 수 없는 메시지입니다(42자)."`

채널 이름 모양·전송 고유의 예시(거절 코드가 든 `error` 등)는 전송 부록에 있다. 예시의 채널 이름은 모양을 정하지 않는다. T1 의 답을 쓴다.

## 7. 거부 응답

본문은 앱 공통 오류 JSON 이고 `message` 칸을 둔다. SSE(EventSource)는 이 상태·본문을 읽지 못해, FE 가 연결이 닫힌 뒤 같은 URL 에 상태 확인 요청을 1회 보낸다. fetch 스트림은 연결 응답에서 바로 읽는다(SKILL.md 3단계 2).

| 상황 | 상태 | 본문 `message` | FE 처리 |
| - | - | - | - |
| 인증 없음·만료(토큰·세션) | 401 | 공통 인증 오류 | D10 갱신 → 실패면 멈춤 |
| 권한 없음 | 403 | 이 화면을 볼 권한이 없다는 문구 | 멈춤. 서버 문구 우선 |
| 인증 주체에 테넌트 없음 | 403 | 테넌트를 찾지 못했다는 문구 | 멈춤. 서버 문구 우선 |
| 테넌트 조회 장애 | 503 | 잠시 뒤 다시 시도하라는 문구 | 재연결 유지. 서버 문구 우선 |
| 모니터 꺼짐 | 404 | 경로 없음 | 멈춤. 고정 문구 |

- **403 은 사유 둘을 함께 맡는다.** 서버가 사유마다 다른 `message` 를 싣는다. 화면은 서버 문구를 먼저 쓰므로 FE 는 사유를 가리지 않는다. 화면 고정 문구는 서버 문구가 없을 때만 쓰는 대체 문구 하나다(UI.md §7).
  - 권한 없음은 보통 FE 진입 가드가 먼저 막는다. 403 까지 오는 것은 대개 테넌트 없음이라 대체 문구도 그쪽에 맞춘다.
- 인증 오류가 403 이 아니라 401 로 나오는지 테스트로 고정한다. 예외 처리 범위 밖 엔드포인트는 인증 미들웨어·가드가 상태를 정한다. 미인증을 기본 403 으로 내는 프레임워크가 있다.

## 8. 버스 메시지(인스턴스 간, D9)

```json
{ "tenantId": "tenant-001", "event": { "...": "§3 의 객체" } }
```

- 받은 인스턴스는 `tenantId` 로 연결을 골라 `event` 만 보낸다.

## 9. 변경 규칙

- 필드를 더할 때: BE 가 먼저 null 로 싣고, FE 가 읽기 시작한다. 계약 테스트에 그 칸을 더한다.
- 필드를 뺄 때: FE 가 먼저 읽지 않게 바꾼다. 그 뒤 BE 에서 뺀다.
- 본 처리의 봉투·채널·직렬화는 이 계약과 무관하다. 모니터 때문에 바꾸지 않는다. 직렬화 고정 테스트가 지킨다.
