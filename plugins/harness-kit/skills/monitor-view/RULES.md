# 판정 규칙 — 순수함수 명세와 테스트 사례

화면의 모든 판정은 아래 순수함수로 만든다. 컴포넌트는 결과를 그리기만 한다.
같은 판정을 두 자리에 쓰지 않는다. 지표·패널·상세가 같은 함수를 부른다.
함수 이름은 예시다. 프로젝트 관례로 바꿔도 된다. 규칙은 전송과 무관하다.

**사례 수 세는 법**(SKILL.md 4단계 게이트)

- 사례표의 행 하나가 테스트 사례 하나다.
- 한 칸에 입력이 `·` 로 여럿 적혀 있으면(예: `null · 999`) 입력마다 하나로 센다.
- 세지 않는 표는 다섯뿐이다: §2 판정 순서 표 · §4 결과 6종 표 · §4-1 행 칸 표 · §12 입력 칸 표 · §12 출력 칸 표. 그 밖의 표는 모두 사례표다(§8-1 결과 → 두 칸 표, §12 입력 → reason 표 포함).
- `` `EVENT` — `` 로 시작하는 행은 D2(b)일 때만 센다. D2(a)면 빼고 센다.
- §16·§17 은 현황판(UI.md §14)을 만들 때만 센다. 다른 절의 `` `현황판` — `` 로 시작하는 행도 같다.
- 0단계에서 「해당 없음」으로 뺀 절(D2 의 짝 관련 절, D4 의 패널)은 그 절의 표를 빼고 센다.
- 표 밖의 규칙 문장도 구현 대상이다. 게이트는 표 행만 센다.

**`EVENT` 행**(D2(b))은 짝·처리 결과·대기·지표에서 빠지고 송신 배지만 받는다. 각 절의 `EVENT` 행이 그 절의 규칙이다.

상수는 D11 의 값이다. 아래 사례는 기준 구현 값으로 적었다: `RESPONSE_TIMEOUT_MS` 30 000 · `LATENCY_WARN_MS`·`LATENCY_DANGER_MS` 1 000·4 000 · `PANEL_IDLE_MS` 10 000 · `NEW_ROW_MS` 2 000 · `EARLY_RESPONSE_WINDOW_MS` 10 000.

입력 꼴: 버퍼 항목 = `{ message, receivedAt }`. `receivedAt` 은 브라우저가 받은 epoch ms 다.
짝을 맺은 항목에는 기억이 붙는다(§3): 응답은 `pairedRequest`, 먼저 온 응답과 짝인 요청은 `pairedResponse`.
버퍼는 최신순이다(맨 앞이 가장 최근). 「키」는 상관 키(`correlationId`)다.
함수마다 이름 옆에 `입력 → 출력` 을 적었다. 이름은 예시지만 입력·출력 칸은 지킨다.

## 1. `parseMessage(value) → message | null`

계약 검사. 식별에 필요한 칸이 틀리면 null 이다. 호출측은 null 을 버리고 버린 건수를 남긴다.

| 입력 | 기대 |
| - | - |
| 객체가 아님 · `id` 가 빈 문자열 | null |
| `direction` 이 두 값 밖 | null |
| `kind` 가 계약 값 밖(예: `null`) | null — D2 가 이 경우를 계약에서 없앴는지 확인한다 |
| `EVENT` — `kind: "EVENT"`, D2(b) | 통과 |
| `kind: "EVENT"`, D2(a) | null(계약 위반). 이 행은 D2(a)일 때만 센다 |
| 빈 문자열 `correlationId`·`action`·`sendResult` | 그 칸 null |
| `success` 가 `"true"`(문자열) | `success` null |
| `payload` 없음 | `payload` null |

## 2. 짝 — `decidePairStep(entry, candidates) → step` · `pairMessages(entries) → { responseOf, requestOf }`

짝은 **브라우저 수신 순서**로 맺는다. 오래된 것부터 훑는다. 전제: 같은 테넌트 이벤트가 기록 순서대로 브라우저에 닿는다(버스 순서, D9 「버스 확인 항목」). 이 전제가 깨지면 아래 「응답이 앞설 수 없다」도 깨진다.

- 짝 후보는 **키마다 마지막 요청 하나**다. 응답은 그 요청이 아직 짝이 없을 때만 그것과 짝이다.
  - 짝이 맺히면 후보를 비운다. 그래서 한 요청에는 먼저 받은 응답 하나만 짝이다. 뒤 응답은 짝 없음이다.
  - 마지막 요청보다 앞선 같은 키 요청(재전송 전 요청)은 후보가 아니다. 자기 상태(대기·시간 초과)로 판정한다.
- **응답이 요청보다 먼저 올 수 있다.** A→B 요청 이벤트는 송신 확인 시점에 나간다(D1). 그 `at` 은 확인 시각이다(CONTRACT.md §3). 확인이 늦으면 B 의 응답이 먼저 온다.
  - 짝 없는 B→A 응답은 짧은 창(`EARLY_RESPONSE_WINDOW_MS`, 그 응답의 브라우저 수신 시각부터) 동안 기억한다.
  - 창 안에 같은 키의 A→B 요청이 오면 그 요청과 짝이다. 요청은 대기를 거치지 않고 그 응답의 결과로 끝난다.
  - 방향은 B→A 응답 / A→B 요청으로만 한정한다. B→A 요청은 받은 즉시 기록되고 A 의 응답은 처리 뒤에 나가서, 응답이 앞설 수 없다.
  - 창 안에 같은 키 응답이 여럿이면 **먼저 온 것 하나만** 후보다. 뒤 응답은 기억하지 않고 짝 없음이다.
  - 창이 지나면 기억을 놓는다. 그 응답은 짝 없음으로 굳는다. 그 뒤 온 요청은 대기로 시작한다.
  - 받을 때 이미 짝을 맺은 응답(요청이 밀려나 기억으로 짝을 잇는 응답, §3)은 기억하지 않는다.
  - 먼저 온 응답과 맺은 짝의 소요가 음수면 비운다(§6). 0 으로 자르지 않는다.
- 키가 null 이면 짝을 찾지 않는다.

**판정 순서는 순수함수 하나다** — `decidePairStep`. 모니터(`pairMessages`)와 현황판(§16 `recordBoardMessage`)이 같은 함수를 부른다.

- 입력 `entry` = 버퍼 항목. `candidates` = `{ openRequest, earlyResponse }`.
  - `openRequest`: 같은 키의 마지막 요청 메시지. 그 요청이 이미 짝이 있거나 요청이 없으면 null.
  - `earlyResponse`: 같은 키로 기억해 둔 응답 항목. 없으면 null. 창 판정은 함수 안에서 한다.
- 출력 `step` 6종. 위에서부터 처음 맞는 것이다.

| 순서 | 조건 | step | 호출측이 할 일 |
| - | - | - | - |
| 1 | 키 없음 | `NO_KEY` | 아무것도 안 한다 |
| 2 | 응답, `openRequest` 있음 | `PAIR_WITH_REQUEST` | 짝을 잇고 후보를 비운다 |
| 3 | 응답이고 셋 중 하나: A→B 응답 · `pairedRequest` 있음 · 창 안 `earlyResponse` 있음 | `UNPAIRED_RESPONSE` | 짝 없음. 기억하지 않는다 |
| 4 | 그 밖의 응답 | `HOLD_RESPONSE` | 이 응답을 그 키의 `earlyResponse` 로 기억한다(창 지난 기억은 바꾼다) |
| 5 | A→B 요청, 창 안 `earlyResponse` 있음 | `PAIR_WITH_EARLY_RESPONSE` | 짝을 잇는다. 기억을 지운다. 이 요청은 짝 있는 마지막 요청이다 |
| 6 | 그 밖의 요청 | `OPEN_REQUEST` | 이 요청을 그 키의 마지막 요청으로 둔다 |

- 창 안 = `entry.receivedAt − earlyResponse.receivedAt < EARLY_RESPONSE_WINDOW_MS`.
- 후보를 자료구조에서 꺼내고 결과를 반영하는 일은 호출측(어댑터)이 한다. 모니터는 버퍼를 받은 순서로 훑는다. 현황판은 기억 지도에서 꺼낸다.
- 두 어댑터는 **계약 테스트**로 묶는다. 같은 메시지열을 넣으면 지표·결과 분포·방향·짝 없는 응답·참여자·action 이 같아야 한다. 메시지열에는 정순·역순(먼저 온 응답)·중복·재전송·응답 없음을 섞고, 메시지를 받을 때마다 비교한다. 끝 상태만 비교하면 중간 상태의 갈림(먼저 온 응답이 짝 없음으로 셌다가 옮겨지는 순간 등)을 못 잡는다.

| 수신 순서(오래된 → 최근) | 기대 |
| - | - |
| Rq(k1) → Rs(k1) | Rq↔Rs |
| Rq1(k1) → Rq2(k1) → Rs(k1) | Rq2↔Rs. Rq1 은 대기 → 시간 초과 |
| Rq1(k1) → Rq2(k1) → Rs(k1) → Rs'(k1) | Rq2↔Rs. Rs' 는 짝 없음. Rq1 은 시간 초과 |
| Rq(k1) → Rs1(k1) → Rs2(k1) | Rq↔Rs1. Rs2 는 짝 없음, 소요 없음 |
| Rq(null) → Rs(null) | 짝 없음 |
| Rq(k1) → Rq(k2) → Rs(k2) → Rs(k1) | Rq(k2)↔Rs(k2), Rq(k1)↔Rs(k1) |
| B→A Rs(k1) → (창 안) A→B Rq(k1) | Rq 가 오기 전 Rs 는 요청 없음. Rq 가 오면 Rq↔Rs. Rq 는 대기 없이 Rs 의 처리 결과. Rq `at` 이 Rs 보다 늦으면 소요 없음 |
| B→A Rs(k1) → (창 안) A→B Rq(k1), Rq `at` 이 Rs 보다 앞섬 | Rq↔Rs. 소요 = 두 `at` 차이 |
| B→A Rs(k1) → (창 지남) → A→B Rq(k1) | 짝 없음. Rs 는 요청 없음으로 굳는다. Rq 는 대기 → 시간 초과 |
| A→B Rs(k1) → (창 안) B→A Rq(k1) | 짝 없음. Rs 는 요청 없음, Rq 는 대기 |
| B→A Rs(k1) → B→A Rs'(k1) → (창 안) A→B Rq(k1) | Rq↔Rs. Rs' 는 짝 없음 |
| `EVENT` — Rq(k1) → EVENT(k1) → Rs(k1) | Rq↔Rs. EVENT 는 짝에 들지 않는다 |

## 3. `rememberPair(buffer, entry) → entry`

새 메시지를 버퍼에 넣기 **전에** 부른다. 받은 버퍼(멈춘 화면 버퍼가 아니다)를 넘긴다. §2 규칙으로 짝이 맺히면 상대 정보를 그 항목에 붙인다.

- 응답이 요청과 짝이면 요청의 `{id, action, at, elapsedMs}` 를 응답 항목에 붙인다(`pairedRequest`). 요청이 상한 때문에 밀려나도 응답이 action·소요를 잇는다.
- 요청이 먼저 온 응답과 짝이면 응답의 `{id, success}` 를 요청 항목에 붙인다(`pairedResponse`). 응답이 먼저 밀려나도 요청이 결과를 잇는다.
- 기억은 그 항목에 붙어 항목과 함께 사라진다. 짝이 없으면 그대로 돌려준다. 기억이 붙은 항목은 이미 짝이 있어, 뒤 메시지가 다시 노리지 않는다.

| 상황 | 기대 |
| - | - |
| 버퍼에 짝 요청 있음 | 응답에 기억이 붙는다. `elapsedMs` = §6 |
| 짝 요청 없음 · 이미 다른 응답과 짝 | 그대로 |
| 요청을 넣은 뒤 그 요청이 버퍼에서 밀려남 | 응답 행: action·소요 유지, "요청이 밀려남" 표시. "처음부터 요청 없음"과 다르다 |
| B→A Rs → (창 안) A→B Rq 뒤 Rs 만 밀려남 | 요청 행: 기억한 결과 유지. 비교표 응답 칸은 "응답이 밀려남" 안내 |
| 응답이 밀려난 요청에 같은 키 응답이 또 옴 | 짝 없음. 한 요청에 응답 하나다 |
| 요청이 밀려난(짝을 기억한) 응답 뒤 창 안에 같은 키 A→B 요청 | 짝 없음. 그 응답은 다시 짝짓지 않는다 |

## 4. `resolveResults(entry, responseOfRequest, nowMs) → badge[]`

`responseOfRequest` = 요청의 짝 응답 메시지(정순 짝이든 먼저 온 응답이든). §3 의 항목 칸 `pairedResponse`(먼저 온 응답의 기억만)와 다르다. 버퍼에서 밀려났으면 기억(§3). 요청이 아니거나 짝이 없으면 null. 처리 결과(`success`)만 본다.

결과 6종

| 키 | 아이콘 | 라벨 | 톤 |
| - | - | - | - |
| `SUCCESS` | ✓ | 처리 성공 | success |
| `FAIL` | ✕ | 처리 실패 | danger |
| `SEND_REJECTED` | ↯ | 송신 거절 | transport |
| `SEND_FAIL` | ↯ | 송신 실패 | transport |
| `WAIT` | ◷ | 대기 | neutral |
| `TIMEOUT` | ⚠ | 시간 초과 | warning |

- 처리 실패와 송신 둘은 원인이 다르다. 처리 실패는 요청을 받은 쪽의 처리 문제다. 송신 거절·송신 실패는 전송 단계의 문제다. 그래서 톤과 아이콘을 가른다(`transport`).
- 송신 둘은 같은 톤·아이콘이다. 라벨 글자로 구분한다.
- 결과마다 톤을 한 번만 적는다(결과 상수). 톤 → 색은 테마 파일의 표 하나가 정한다(UI.md §9).
- 판정 모델은 늘 결과 6종이다. 송신 거절이 일어날 수 없는 전송에서 그 칩을 숨기는 것은 표시 규칙이다(UI.md §3). 결과 키·사례는 바꾸지 않는다.

규칙

- 송신 배지: OUTBOUND 만. `SENT`·null → 없음, `REJECTED` → 송신 거절, `FAILED`·`NOT_SENT` → 송신 실패, 그 밖 → 원문 중립 배지(결과 키 없음).
- 응답 행: [처리 결과(`success`)] + [송신 배지].
- 요청 행: 송신 거절·실패가 있으면 **그것만**이다. 응답을 기다릴 이유가 없다.
  - 아니면 [중립 송신 배지] + 짝 응답의 처리 결과.
  - 짝 응답이 없으면 `isResponseOverdue` 로 대기 또는 시간 초과다.
- `EVENT` 행: 송신 배지만이다. 처리 결과·대기·시간 초과는 없다.

| 행 | 입력 | 기대 |
| - | - | - |
| 응답 | INBOUND, `success=true` | [처리 성공] |
| 응답 | INBOUND, `success=false` | [처리 실패] |
| 응답 | OUTBOUND, `success=true`, `REJECTED` | [처리 성공, 송신 거절] |
| 응답 | `success=null`, `SENT` | [] (결과 없음) |
| 요청 | OUTBOUND, `FAILED` | [송신 실패] |
| 요청 | OUTBOUND, `NOT_SENT` | [송신 실패] |
| 요청 | OUTBOUND, `REJECTED`, 짝 응답 `success=true` | [송신 거절] |
| 요청 | OUTBOUND, `SENT`, 짝 응답 `success=true` | [처리 성공] |
| 요청 | 짝 없음, now − receivedAt = 29 999 | [대기] |
| 요청 | 짝 없음, now − receivedAt = 30 000 | [시간 초과] |
| 요청 | 시간 초과 뒤 짝 응답 `success=false` 도착 | [처리 실패] |
| 요청 | OUTBOUND, `"QUEUED"`, 짝 없음, 5초 | [QUEUED(중립), 대기] |
| `EVENT` | INBOUND | [] |
| `EVENT` | OUTBOUND, `FAILED`, 60초 경과 | [송신 실패] — 시간 초과 없음 |

### 4-1. 행 만들기 — `buildRows(entries, nowMs) → row[]`

최신순 버퍼 → 같은 순서의 행. 짝은 §2 를 한 번 돌려 정한다. 두 행을 하나로 합치지 않는다. 목록·패널·지표·현황판이 모두 이 행을 쓴다.

| 행 칸 | 값 |
| - | - |
| `message` | 그 항목의 메시지 |
| `action` | 요청·`EVENT`: 자기 `action`. 응답: 자기 값 → 짝 요청 → 기억(§3) 순. 모두 없으면 null |
| `pairId` | 짝 메시지 `id`. 버퍼에 짝이 없으면 null(기억만 있어도 null) |
| `results` · `resultKeys` | §4 배지와 그 결과 키. 중립 배지는 키가 없다 |
| `elapsedMs` | 응답만. 짝 요청이 있으면 §6, 없으면 기억의 값, 그것도 없으면 null. 요청은 null |
| `awaitingResponse` | 요청이 짝도 기억도 없다 |
| `requestMissing` · `requestEvicted` | 응답만. 버퍼에 짝 요청이 없다 · 그중 기억이 있다(밀려남) |
| `responseEvicted` | 요청만. 버퍼에 짝 응답이 없고 기억이 있다 |
| `sender` · `receiver` | §14 칩 |
| `isNew` | `nowMs − receivedAt < NEW_ROW_MS` |
| `time` | 서버 `at` 의 표시 글자 |

## 5. `isResponseOverdue(receivedAt, nowMs)`

## 6. `pairElapsedMs(request, response) → ms | null`

`response.at − request.at`. **서버 시계**다. 둘 중 하나라도 없거나 읽을 수 없거나 차이가 음수면 null(화면 「—」, 평균에서 뺀다).

- **전제: 두 `at` 을 같은 A 인스턴스가 잰다.** 이 전제는 수신 방식에 달렸다. D9 의 확인 항목으로 확인하고 결정 기록에 적는다.
- 음수는 결함이 아니다. A→B 요청의 `at` 은 송신 확인 시각이라 먼저 온 응답(§2)보다 늦을 수 있다. 실제 소요를 알 수 없어 비운다.
- 소비가 밀리면(T12) INBOUND `at` 은 소비 시각이다. B→A 요청의 처리 소요가 밀린 만큼 짧게 보이고, 재시작 뒤 밀린 메시지는 「방금 받은 요청」으로 보인다. 가이드 「한계」에 적는다. 메시지에 실린 보낸 시각(`sentAt`)은 다른 시계라 소요에 쓰지 않는다.
- 브라우저 수신 시각은 팬아웃·스트림 지연이 섞여 쓰지 않는다. 아래 표는 날짜 부분(`2026-01-15T`)을 줄여 적었다.

| 요청 `at` | 응답 `at` | 기대 |
| - | - | - |
| `10:00:01.000+09:00` | `10:00:01.250+09:00` | 250 |
| `10:00:01.000+09:00` | `01:00:01.000Z` | 0 (같은 순간) |
| `10:00:02.000+09:00` | `10:00:01.000+09:00` | null (음수) |
| `""` | `10:00:01.000+09:00` | null |

## 8. `computeMetrics(rows) → { requests, responses, waiting, avgLatencyMs, failureRate }`

**지금 보이는 행 기준**이다(필터 적용 뒤).

- `requests` · `responses`: 그 종류의 행 수.
- `waiting`: 결과에 대기가 있는 요청 수. 시간 초과는 뺀다.
- `avgLatencyMs`: 소요가 있는 행의 평균, 반올림. 없으면 null(화면 「—」).
- `failureRate`: 분모 = 결과 키가 하나 이상이고 대기가 없는 행. 분자 = 그중 실패 계열(처리 실패·송신 거절·송신 실패·시간 초과)이 하나라도 있는 행. %, 소수 1자리. 분모 0 이면 null.
- `EVENT` 행은 다섯 지표 어디에도 세지 않는다. 지표는 요청·응답 교환을 잰다.

| 보이는 행 | 기대 |
| - | - |
| 요청[처리 성공], 응답[처리 성공](250ms), 요청[대기], 요청[시간 초과] | requests 3 · responses 1 · waiting 1 · avg 250 · rate 33.3 |
| 요청[QUEUED 중립, 대기] 하나 | waiting 1 · rate null |
| 응답[처리 성공, 송신 거절] 하나 | rate 100.0 |
| 빈 목록 | 0 · 0 · 0 · null · null |
| `EVENT` — 응답[처리 성공](250ms), EVENT[송신 실패] | requests 0 · responses 1 · waiting 0 · avg 250 · rate 0.0 |

- 지표는 행 하나의 몫(`metricTallyOf`)을 더하고, 마지막에 지표로 바꾼다(`metricsFromTally`). 모니터 머리는 보이는 행을 더하고, 현황판(§16)은 받은 행을 누적한다. 두 화면이 같은 정의를 쓴다.
  - `metricTallyOf(kind, resultKeys, elapsedMs) → tally`. tally = `{requests, responses, waiting, latencySum, latencyCount, settled, failed, processFailed, sendFailed}`. 행 하나면 칸마다 0 또는 1 이다(`latencySum` 만 ms).
    - `settled` = 결과 키가 있고 대기가 없다. `failed`·`processFailed`·`sendFailed` 는 `settled` 일 때만 센다(§8-1).
  - `addTally(a, b, sign) → tally`: 칸마다 `a + sign × b`. `sign` 은 1 또는 −1 이다. 현황판이 결과가 바뀐 행의 이전 몫을 뺄 때 −1 을 쓴다.
  - `metricsFromTally(tally) → metrics`: `avgLatencyMs` = `latencySum ÷ latencyCount` 반올림(0 이면 null). `failureRate` = `failed ÷ settled` %, 소수 1자리(분모 0 이면 null). 나머지 셋은 그대로다.

### 8-1. 실패 두 칸 — `failureKindsOf(resultKeys)` · `failureKindStats(processFailed, sendFailed)`

「실패」를 원인으로 나눠 보이는 칸이다. 패널 머리(§11)와 현황판 카드(UI.md §14)가 쓴다.

- **처리 실패** = 결과에 처리 실패가 있다. **송신 문제** = 결과에 송신 거절·송신 실패가 있다. 송신 문제 라벨은 결과 상수 옆 한 곳에 둔다(예: `FAILURE_KIND`).
- 두 칸이 세는 결과는 톤으로 고른다. 처리 실패 칸은 `danger` 결과, 송신 문제 칸은 `transport` 결과다. 결과 종류를 새로 더할 때는 톤만 맞추면 된다.
- 한 행이 두 칸에 모두 들 수 있다. 각각 한 번씩 센다.
- **시간 초과는 두 칸 어디에도 없다.** 실패율(§8)의 분자에만 든다. 실패율은 나누지 않은 합계 그대로다.
- 「실패」로 정렬할 때는 두 칸이 아니라 합계(실패율의 분자, 시간 초과 포함)로 정렬한다.
- 칸 값은 0 이면 톤 없음(보통 글자색)이다. 아이콘은 자리만 차지한다. 숫자 포맷은 §15 공용 포맷터다.
- 누적 집계는 결과가 확정된 행(대기·결과 없음 제외)에서만 두 칸을 센다. 실패율의 분모와 같은 행이다.

| 결과 | 처리 실패 | 송신 문제 |
| - | - | - |
| [처리 실패] | 예 | 아니요 |
| [처리 성공, 송신 거절] | 아니요 | 예 |
| [처리 실패, 송신 실패] | 예 | 예 |
| [송신 실패] | 아니요 | 예 |
| [시간 초과] | 아니요 | 아니요 — 실패율에만 |
| [대기] · [] | 아니요 | 아니요 |

| `failureKindStats` 입력 | 기대 |
| - | - |
| (2, 0) | 처리 실패 2(톤 danger) · 송신 문제 0(톤 없음) |
| (1 234, 5) | 값 글자 `1,234` · `5` |

## 9. 필터 · 패싯 건수 — `filterRows(rows, filter) → row[]` · `countFacets(rows, filter) → 그룹별 { total, counts }`

- 조건 `filter` = `{ direction, results[], parties[], actions[], text }`. `direction` 은 하나(전체 또는 방향 키). 나머지 셋은 키 배열이고 빈 배열 = 전체다.
- 그룹 키(행 하나 → 키): 방향 = 메시지 `direction` · 결과 = `resultKeys` · 참여자 = 보낸·받는 칩 키 둘(§14 `partyKeyOf`) · action = 행 `action`, 없으면 「action 미상」 키.
- `filterRows`: 검색어와 네 그룹 조건을 모두 건다. 순서는 그대로다.
- `countFacets`: 그룹마다 `total` = 그 그룹의 [전체] 칩 건수, `counts` = 키 → 건수.
- 검색어는 채널·action·상관 키·보낸/받는 참여자 ID 를 대소문자 무시 부분 일치로 본다.
- 참여자는 보낸 쪽·받는 쪽 중 하나라도 맞으면 통과다.
- 결과가 없는 행은 결과 그룹이 전체일 때만 보인다.
- **결과 칩을 모두 고르면 전체로 접는다.** 고른 결과 키가 보이는 결과 칩의 키 전부가 되면 `results` 를 빈 배열(전체)로 바꾼다. 그래서 결과 없는 행도 다시 보인다.
  - 기준은 보이는 칩이다. 송신 거절 칩을 숨겼으면(UI.md §3) 남은 5개가 전부다. 보이는 결과 키 목록은 상수 한 곳에 두고 칩 그리기·접기·쿼리 읽기(§17)가 같이 쓴다.
  - 접기는 결과 그룹만 한다. 참여자·action 은 후보가 계속 늘어 「지금 후보 전부」가 전체가 아니다(§9-1). 방향은 하나만 고른다.
- 행의 action 은 행 칸 `action`(§4-1)이다. null 이면 「action 미상」 키다. 종류는 필터 그룹이 아니다.
- **패싯 건수**: 그룹 G 의 칩 건수 = 행을 거른 뒤 G 의 키로 센 값이다. 거를 때 **검색어는 늘 건다.** G 자기 조건만 빼고, 다른 그룹 조건은 모두 건다. 한 행이 G 에서 키 둘을 가지면 양쪽에 한 번씩 센다.

| 상황 | 기대 |
| - | - |
| 결과 칩 [처리 실패]를 누름 | 결과 그룹 칩 건수는 그대로다. 방향·action 건수는 처리 실패 행만으로 다시 센다 |
| 검색어 `REQ-7C` 를 넣음 | 모든 그룹 칩 건수가 검색 일치 행만으로 줄어든다(결과 그룹 포함) |
| 응답[처리 성공, 송신 거절] 1행 | 처리 성공 1 · 송신 거절 1 |
| 결과 필터 = [처리 성공], 결과 없는 응답 | 그 응답은 안 보인다 |
| 검색어 `REQ-7C` | `req-7c1f` 행이 보인다 |
| `EVENT` — 결과 필터 = [송신 실패], EVENT[송신 실패] | 보인다 |
| `EVENT` — 결과 필터 = [처리 성공], EVENT[] | 안 보인다 |
| 결과 칩 6개를 차례로 모두 고름 | 결과 [] (전체). 결과 없는 응답이 다시 보인다 |
| 송신 거절 칩 숨김, 보이는 5개를 모두 고름 | 결과 [] (전체). 결과 없는 응답이 다시 보인다 |
| 송신 거절 칩 보임, 6개 중 5개를 고름 | 접지 않는다. 결과 없는 응답은 안 보인다 |

### 9-1. 참여자 조건 — 검색형 다중 선택

참여자는 수백이 될 수 있다. 칩을 늘어놓지 않고 검색칸 + 체크 목록으로 고른다(UI.md §6).

- 후보 = 지금 행의 보낸·받는 칩 키. 처음 나타난 순서다. ID 를 모르는 칩(§14 「알 수 없음」 등)도 후보 하나다.
- 빈 선택 = 전체 = 조건 없음이다. 나중에 나타나는 참여자도 보인다. 「고른 것 없음」 상태는 없다.
- 체크 하나는 그 키만 켜고 끈다. 결과 칩처럼 "모두 고르면 전체로 접기"(§9)를 하지 않는다. 후보가 계속 늘어 "지금 후보 전부"가 전체가 아니다.
- 검색: 키(ID 원문)나 칩 라벨에 부분 일치, 대소문자 무시.
- `[전체 선택]`: 고른 것에 검색 일치분(검색어가 없으면 지금 후보 전부)을 더한다. 빈 선택과 다르다 — 나중에 나타나는 참여자는 들지 않는다.
- `[선택 해제]`: 고른 것에서 검색 일치분을 뺀다. 검색어가 없으면 빈 선택(전체)으로 돌아간다.
- 목록 정렬: 연 순간 고른 것이 맨 위, 그다음 건수 많은 순, 같으면 처음 나타난 순. 「연 순간」은 열 때 한 번 찍는다. 체크할 때마다 줄이 뛰지 않게 한다.
- 목록에 상한이 없다. 보이는 줄만 그린다(가상 스크롤, UI.md §6).

| 상황 | 기대 |
| - | - |
| 선택 [], 후보 [a, b, c], 검색 없음, `[전체 선택]` | [a, b, c]. 뒤에 나타난 d 는 안 보인다 |
| 선택 [a], 검색이 b 하나와 일치, `[전체 선택]` | [a, b] |
| 선택 [a, b], 검색 없음, `[선택 해제]` | [] (전체) |
| 선택 [a, b], 검색이 b 하나와 일치, `[선택 해제]` | [a] |
| 연 순간 선택 [c], 건수 a 3 · b 5 · c 1 | 줄 순서 c, b, a |
| 닫힌 버튼 — 선택 [] · [a] · [a, b] | `전체 (N개)` · a 칩 라벨과 그 색 견본 · `2개 선택`(견본 없음) |

## 10. 멈춤 — `shouldResync(prev, next)` · `countNewWhileHeld(buffer, frozen)`

멈춤 사유는 둘이다: 일시정지 버튼, 목록을 맨 위에서 내려 봄. 멈춰도 **수신은 받은 버퍼에 계속 쌓인다.** 보이는 목록만 멈춘다.

| prev → next | `shouldResync` |
| - | - |
| 사유 없음 → 일시정지 | true (그 순간 버퍼를 붙잡는다) |
| 일시정지 → 일시정지 + 내려 봄 | false |
| 일시정지 + 내려 봄 → 내려 봄 | true (풀린 사유가 있다. 남은 사유로 다시 붙잡는다) |
| 내려 봄 → 사유 없음 | true |

`countNewWhileHeld`: 멈춘 버퍼 맨 앞 항목이 받은 버퍼에서 몇 번째인가. 없으면(밀려남) 받은 버퍼 길이다. 멈춘 버퍼가 비었으면 받은 버퍼 길이다.

| 받은 버퍼 | 멈춘 버퍼 | 기대 |
| - | - | - |
| [e5, e4, e3, e2] | [e3, e2] | 2 |
| [e9, e8] (e3 밀려남) | [e3, e2] | 2 |
| [e2, e1] | [] | 2 |

- 상한을 줄이면 두 버퍼를 함께 자른다(`trimToLimit`). 오래된 것(맨 뒤)부터 버린다.

| `trimToLimit(버퍼, 상한)` | 기대 |
| - | - |
| [e5, e4, e3, e2, e1], 3 | [e5, e4, e3] |
| [e2, e1], 3 | [e2, e1] |

## 11. 패널 — `panelKeyOf` · `buildPanels` · `selectPanelContent` · `isPanelActive` · 활동 시계

- `panelKeyOf(message) → 키`: 상대 ID(D4). INBOUND 는 보낸 쪽, OUTBOUND 는 받는 쪽이다. 없으면 「ID 없음」 칸 키(상수 하나).
- `buildPanels(rows) → panel[]`: 필터 결과 행(최신순) → 줄(쌍) → 칸. 칸 = `{key, chip, lines, requests, responses, failures, lastTime, lastActivityAt, pending, idle}`. `idle` 은 여기서 늘 false 다.
- 줄 키 = 요청 쪽 `panelKeyOf` → 응답 쪽 → 「ID 없음」 순이다. 쌍 중 한쪽에 있으면 그것(요청 쪽 우선), 둘 다 없으면 「ID 없음」 칸이다.
- `EVENT` 행은 쌍이 아니라 혼자 한 줄이다. 칸 키는 같은 규칙으로 정한다.
- D4 가 다른 묶음 키를 정했으면 그 키로 바꿔 읽는다.
- 칸 대상은 필터 결과 그대로다. 줄이 없는 칸은 만들지 않는다.
- 줄 위치는 그 쌍에서 가장 최근에 받은 메시지 자리다. 응답이 오면 그 쌍이 맨 위로 온다.
- **칸 순서는 최근 메시지 순이다.** 가장 최근에 받은 메시지가 든 칸이 맨 앞이다. 쉬는 칸은 자연히 뒤로 간다.
- 칸 머리 건수: 요청 수 · 응답 수 · 실패 두 칸(§8-1). 실패 두 칸은 줄(쌍) 단위로 센다.

| 칸의 마지막 메시지 수신 순서(오래된 → 최근) | 기대 칸 순서 |
| - | - |
| `b-01` → `b-02` → `b-01` | `b-01`, `b-02` |

| 행·쌍 | 기대 칸 |
| - | - |
| B→A 요청(보낸 쪽 `b-01`) ↔ A→B 응답(받는 쪽 `b-01`) | `b-01` |
| B→A 요청(보낸 쪽 null) ↔ A→B 응답(받는 쪽 `b-01`) | `b-01` |
| A→B 요청(받는 쪽 null) ↔ B→A 응답(보낸 쪽 `b-02`) | `b-02` |
| 요청 쪽 `b-01` ↔ 응답 쪽 `b-09` | `b-01`(요청 쪽 우선) |
| 짝 없는 B→A 요청(보낸 쪽 null) | 「ID 없음」 |
| `EVENT` — INBOUND(보낸 쪽 `b-03`) | `b-03`, 혼자 한 줄 |

- 내용 방식 `selectPanelContent(panels, content, activityNowMs) → panel[]`: `전체` 는 칸을 그대로 둔다. `활동 중` 은 칸마다 최신 1줄만 두고 `idle = !isPanelActive(칸, activityNowMs)` 를 붙인다.
- **어느 방식이든 칸을 빼지 않는다.** 순서도 그대로다.
- **「쉼」은 `활동 중` 방식 전용이다.** `전체` 방식은 쉼을 판정하지 않는다. 쉬는 칸만 흐리게 그리고 머리에 `쉼` 을 적는다(UI.md §4).
- 활동 중(`isPanelActive`): 응답 대기 요청이 있으면 늘 활동 중이다. 아니면 마지막 활동 뒤 `PANEL_IDLE_MS` 전까지다. `EVENT` 행은 대기가 없다.
- 마지막 활동 = 받은 시각. 시간 초과로 끝난 요청은 받은 시각 + 응답 제한시간이다.
- 활동 시계 = 브라우저 시계 − 일시정지한 시간. 일시정지 동안 멈춘다.

| 칸(`활동 중` 방식) | 활동 시계 now − 마지막 활동 | 기대 |
| - | - | - |
| 대기 요청 있음 | 60 000 | 활동 중 |
| 대기 없음 | 9 999 | 활동 중 |
| 대기 없음 | 10 000 | 쉼 — 칸은 남고 흐리게 보인다 |
| 대기 없음, 마지막 활동 뒤 8초 일시정지 후 재개, 실제 경과 12초 | 4 000 | 활동 중 |
| `활동 중` 방식, 칸에 줄 3개 | — | 최신 1줄만 |
| `전체` 방식, 쉬는 칸 | — | 줄 그대로, 쉼 표시 없음 |

## 12. 연결 — `classifyStreamProbe` · `resolveConnectionView` · `resolveTransportView` · `resolveEmptyState`

`classifyStreamProbe({status, message, refresh}) → issue | null` — 닫힌 연결 하나의 상태를 판정한다. 상태의 출처는 D8 수단마다 다르다(SSE 는 상태 확인 응답, fetch 스트림은 연결 응답, SKILL.md 3단계 2).

| 입력 칸 | 형식 | 뜻 |
| - | - | - |
| `status` | number \| null | 닫힌 연결의 상태. 네트워크 오류면 null |
| `message` | string \| null | 응답 본문의 `message`. 없거나 읽지 못하면 null |
| `refresh` | `"OK"` \| `"FAILED"` \| `"NONE"` | 401 일 때만 본다. 호출측이 이 401 에 대해 갱신(D10)을 1회 부른 결과다. 부르지 않았으면 `NONE`(D10(c) · 상한 도달) |

| 출력 칸 | 형식 | 뜻 |
| - | - | - |
| (전체) | null | 일시 장애. 재연결 지연(D11) 뒤 다시 연다 |
| `reason` | `UNAVAILABLE` · `SESSION_EXPIRED` · `NO_TENANT` · `SERVICE_DOWN` | 아래 표 |
| `message` | string | 화면 문구. 서버 문구를 쓸지는 아래 표 |
| `stop` | boolean | true 면 재연결을 멈춘다 |

| 입력 | reason | 문구 | 멈춤 |
| - | - | - | - |
| 404 | `UNAVAILABLE`(기능 꺼짐) | 고정 문구 | 예 |
| 401, `refresh` = `OK` | 없음(null) | — | 아니요 — 갱신한 인증으로 재연결 |
| 401, `refresh` = `FAILED` · `NONE` | `SESSION_EXPIRED`(인증 만료) | 고정 문구(서버 문구 무시) | 예 |
| 503 | `SERVICE_DOWN`(조회 장애) | 서버 문구, 없으면 고정 문구 | 아니요 |
| 403 · 그 밖 4xx | `NO_TENANT`(테넌트 없음) | 서버 문구, 없으면 고정 문구 | 예 |
| 2xx · 그 밖 5xx · 네트워크 오류(null) | 없음(null) | — | 아니요 — 그냥 재연결 |

- 403 은 권한 없음·테넌트 없음을 함께 맡는다. 서버 문구가 사유를 가린다. FE 는 사유를 나누지 않는다(CONTRACT.md §7).
- **갱신 횟수(D10·D11).** 401 하나에 갱신은 1회다. 같은 401 에 갱신을 되풀이하지 않는다.
  - 갱신이 `FAILED` 면 바로 멈춘다.
  - 갱신이 `OK` 인데 다시 연 연결이 또 401 로 닫히면, 그 401 에 다시 1회 부른다. 이것이 연속 상한(D11)에 닿으면 갱신을 부르지 않고 `NONE` 으로 판정한다.
  - 연결이 `open` 에 닿으면 연속 횟수를 0 으로 되돌린다. 횟수 세기는 호출측 상태다. 판정 함수는 `refresh` 만 본다.
- D10 이 (c) 「갱신 없음」이면 `refresh` 는 늘 `NONE` 이다.

`resolveConnectionView(state, issue)`: 멈춘 문제 > 재연결 중 문제(503) > 상태. 연결이 열리면 호출측이 문제를 지운다.

| state | issue | 기대 |
| - | - | - |
| stopped | 403 | 403 문제 |
| reconnecting | 503 | 503 문제 |
| open | 없음 | 화면 연결됨 |
| reconnecting | 없음 | 화면 재연결 중 |
| idle · connecting | 없음 | 화면 연결 시도 중 |

`resolveTransportView(state, transport, nowMs)`: 전송 연결 표시(UI.md §7). T13 이 「해당 없음」이면 이 함수와 아래 표를 빼고 센다.

- `state` 는 화면 연결 상태(SKILL.md 3단계 2)다. `transport` 는 이번 연결에서 마지막으로 받은 `transportStatus`(CONTRACT.md §2)다. 받지 않았으면 null 이다.
- 화면 연결이 open 이 아니면 전송 상태를 모른다. 마지막으로 받은 값을 쓰지 않는다.
- 호출측은 화면 연결이 open 을 벗어나는 순간 `transport` 를 null 로 지운다. 다시 열린 뒤 새 이벤트가 오기 전까지 지난 연결의 값을 보이지 않는다.
- 미연결 시각은 `changedAt` 의 시:분이다. `changedAt` 이 `nowMs` 와 다른 날이면 날짜를 붙인다.
- `transportStatus` 의 `data` 는 `connected` 가 boolean, `changedAt` 이 문자열일 때만 받는다. 아니면 그 이벤트를 버리고 앞의 값을 둔다. 버린 건수를 개발 콘솔에 남긴다(SKILL.md 3단계 3).

| state | transport | 기대 |
| - | - | - |
| open | null | 확인 중 |
| open | `connected: true` | 연결됨 |
| open | `connected: false`, `changedAt` 이 `nowMs` 와 같은 날 09:58 | 미연결 · `09:58부터` |
| open | `connected: false`, `changedAt` 이 `nowMs` 전날 23:50 | 미연결 · 날짜 + `23:50부터` |
| idle · connecting · reconnecting · stopped | `connected: true`(지난 값) | 확인 불가 |

`resolveEmptyState(issue, receivedCount)`: 연결 문제 > 받은 것 없음 > 걸러져 비었음. 보이는 목록이 비었을 때만 부른다.

- `receivedCount` 는 지금 목록이 그리는 버퍼의 건수다. 멈춘 동안은 멈춘 화면 버퍼의 건수다.
- 패널 보기도 같은 판정이다. 패널은 칸을 빼지 않으므로(§11) 「활동 중인 칸 없음」 상태는 없다.

| issue | receivedCount | 기대 |
| - | - | - |
| 503 | 0 | 연결 문제 |
| 403(멈춤) | 5 | 연결 문제 |
| 없음 | 0 | 받은 것 없음 |
| 없음 | 5 | 걸러져 비었음(「필터 초기화」 버튼은 이때만) |

## 14. 참여자 칩 — `partyChip(id, side, unknownReason) → {id, label, colorIndex}` · `partyKeyOf(chip) → 키`

- 라벨 = 측 접두 + ID 꼬리 N 글자(D12).
- 모를 때: 라벨 = 측 + 괄호 안 사유. `unknownReason` 은 D12 가 정한 사유(모두 받음 · 나눠 받음 · 알 수 없음)다. 받는 끝점을 송신 때 특정할 수 없는 A→B 요청은 앞의 둘 중 하나, 그 밖은 「알 수 없음」.
- **칩 키**(`partyKeyOf`) = ID. 모르면 그 칩의 라벨이다(예: `B(알 수 없음)`·`B(테넌트 전체)`). 필터 조건·패싯 건수·현황판 참여자 카드·모니터 링크가 이 키 하나를 쓴다.
  - 그래서 ID 를 모르는 칩은 측·사유가 같으면 한 후보로 묶인다. 짝 상대의 ID 로 추정해 채우지 않는다.
- **색 = 역할(측)색 2개.** A 쪽 칩은 A 색, B 쪽 칩은 B 색이다. 참여자마다 색을 주지 않는다.
  - 이유: 참여자가 수십~수백이면 색이 겹쳐 구분이 안 된다. 등장 순서로 색을 매기면 화면마다 같은 참여자가 다른 색이 된다.
  - 어느 참여자인지는 칩 글자(측 접두 + 꼬리)로 읽는다. 색만으로 측을 가르지 않는다.
- ID 를 모르는 칩은 역할색을 쓰지 않는다(색 번호 null).

| 입력 | 기대(접두 `A-` 꼬리 5, `B-` 꼬리 4) |
| - | - |
| A 쪽 `svcA-app01` | `A-app01`, A 색 |
| B 쪽 `b-node-7f2a` | `B-7f2a`, B 색 |
| A→B 요청의 받는 쪽 null, 사유 모두 받음 | `B(테넌트 전체)`, 색 없음 |
| A→B 요청의 받는 쪽 null, 사유 나눠 받음 | `B(나눠 받음)`, 색 없음 |
| B→A 응답의 보낸 쪽 null | `B(알 수 없음)`, 색 없음 |
| B 쪽 다른 ID 둘 | 둘 다 B 색 — 글자로 구분한다 |
| A→B 요청 둘의 받는 쪽 null, 사유 같음(모두 받음) | 칩 키 둘 다 `B(테넌트 전체)` — 한 후보 |
| `현황판` — 같은 ID, 다른 화면(모니터·현황판) | 같은 색 |

## 15. 다시 그리기 줄이기 — `sameViewValue` · `reuseUnchangedItems(prev, next, keyOf)`

1초 재판정 틱은 행·패널·카드를 다시 계산한다. 내용이 그대로면 이전 객체를 다시 써서, 바뀐 항목만 다시 그리게 한다. 참여자가 수백일 때 필요하다.

- `sameViewValue(a, b)`: 원시값은 `Object.is`, 배열은 원소 차례로, 일반 객체는 같은 키·같은 값이다. 그 밖의 객체(Map·Set·Date 등)는 같은 참조일 때만 같다. 다르다고 보면 다시 그릴 뿐, 틀리게 그리지 않는다.
- `reuseUnchangedItems`: 키로 이전 항목을 찾고 `sameViewValue` 가 같으면 이전 객체를 쓴다. 모든 항목이 이전 것이고 순서·길이가 같으면 이전 배열 자체를 돌려준다. 그리는 값은 늘 `next` 와 같다.
- 쓰는 곳: 행 목록 · 보이는 행 · 패널 칸 · 현황판 항목 카드. 같은 함수 하나를 쓴다.
- 항목마다 컴포넌트를 두고, props 참조가 같으면 다시 그리기를 건너뛰게 한다. 프레임워크마다 다르다(예: Vue 는 기본, React 는 `React.memo` + 콜백 props 를 `useCallback` 으로 고정). 건너뛰지 않으면 객체를 다시 써도 효과가 없다.
- 집계 객체 → 화면 행 변환은 집계 객체를 키로 메모한다(약한 참조 맵 등). 집계 객체가 그대로면 변환을 다시 하지 않는다.
- 숫자 포맷터는 한 번만 만든다(공용 `formatCount`). 부를 때마다 로캘 포맷터를 새로 만들면(예: JS `toLocaleString()`), 수백 칸에서 한 번 계산이 프레임 예산을 넘는다.

| prev → next | 기대 |
| - | - |
| prev 없음 · 빈 배열 | `next` 그대로 |
| 모든 항목 내용 같음, 순서·길이 같음 | prev 배열 자체 |
| 한 항목만 바뀜 | 그 항목만 새 객체. 나머지는 prev 객체. 배열은 새 배열 |
| 순서만 바뀜 | 항목은 모두 prev 객체. 배열은 새 배열 |
| 항목 안 Map 이 내용은 같고 참조가 다름 | 그 항목은 새 객체(다르다고 본다) |

## 16. 현황판 집계(선택) — `recordBoardMessage` · `tickBoard`

현황판(UI.md §14)은 화면을 연 뒤 받은 메시지를 누적해 센다. 목록 버퍼와 따로 센다. 버퍼에서 밀려나도 누적은 줄지 않는다. 이력 저장은 없다.

- `recordBoardMessage(state, message, receivedAt) → state`: 메시지 하나를 받아 새 상태를 돌려주는 순수함수(reducer)다. 넘긴 상태는 고치지 않는다. `receivedAt` 은 브라우저 수신 시각이다(추이 칸·시간 초과·먼저 온 응답 창의 기준).
- 상태 = 전체 tally·결과 분포 · 방향별 tally·결과 분포 · 짝 없는 응답 수 · 보낸 측 규모 · 참여자·action 별 tally · 기억 중 요청 · 키마다 마지막 기억 요청 · 먼저 온 응답 기억 · 추이 칸 · 놓친 요청 수 · 집계 시작 시각.
- 판정은 모니터 함수를 그대로 부른다. 짝 판정 순서는 §2 `decidePairStep`, 결과·소요는 §4-1, 방향·참여자·action 키는 §9, 지표 몫은 §8 이다.
  - 그래서 같은 메시지에 모니터와 현황판의 판정이 갈리지 않는다. 숫자가 다른 이유는 집계 범위뿐이다. 화면에 그렇게 적는다.
- 요청 결과는 시간이 지나며 바뀐다(대기 → 시간 초과, 늦은 응답 → 그 응답의 결과). 바뀔 수 있는 요청을 기억하고, 바뀔 때 이전 몫을 빼고 새 몫을 더한다.
- **짝 후보는 키마다 마지막 기억 요청 하나다**(§2). 응답은 그 요청하고만 짝짓는다. 짝이 맺히면 그 요청을 놓고 후보를 비운다. 같은 키의 앞 요청은 자기 결과(대기 → 시간 초과)로 남는다.
- **먼저 온 응답**(§2 `HOLD_RESPONSE`)은 받을 때 짝 없음으로 센다. 그리고 창 동안 기억한다.
  - 창 안에 같은 키 A→B 요청이 오면: 그 응답의 짝 없음 몫을 빼고, 요청 방향 줄의 짝 몫으로 다시 센다. 짝 없는 응답 수를 1 줄인다. 요청은 기억하지 않고 그 응답의 결과로 센다.
  - 그 소요(낼 수 있을 때)는 응답을 받은 칸에 넣는다.
  - 창이 지난 기억은 다음 메시지를 받을 때 놓는다. 그 응답은 짝 없음 그대로다.
  - 기억 수는 요청 기억 상한(D11)과 같은 값으로 따로 자른다. 넘으면 먼저 받은 응답부터 놓는다. 놓은 응답은 뒤에 온 요청과 짝짓지 않는다.
- 기억 상한(D11)을 넘으면 가장 먼저 받은 요청부터 놓는다. 받은 지 보관 시간(D11)이 지난 요청도 놓는다. 놓은 뒤 온 응답은 짝 없음이다.
  - 대기 중에 놓은 요청은 결과 없음으로 바꾸고 따로 센다. 화면에 그 건수를 알린다.
- `tickBoard(state, nowMs) → state`: 추이 칸을 이번 분까지 민다. 제한시간을 넘긴 대기 요청을 시간 초과로 바꾼다(한 번만). 보관 시간이 지난 요청을 놓는다. 바뀐 것이 없으면 **같은 상태 객체**를 돌려준다(§15 가 이것에 기댄다).
- **방향 묶음:** 요청과 그 응답을 요청 방향 줄 하나에 센다. 짝 없는 응답은 방향 줄에서 빼고 전체 지표·결과 분포에만 센다. 뺀 건수를 화면에 알린다. 그래서 줄마다 응답 수는 요청 수를 넘지 않는다.
- **보낸 측 규모:** 요청·응답·참여자를 보낸 측(A·B)으로 나눠 센다. 참여자 수 = 메시지를 보낸 고유 참여자 수다. 보낸 쪽이 없는 메시지는 세지 않고 그 건수를 알린다.
- **결과 분포:** 결과 6종 건수와 비율. 비율 = 그 결과인 메시지 ÷ 결과가 하나라도 있는 메시지. 결과 둘인 메시지는 양쪽에 센다. 그래서 비율 합은 100% 를 넘을 수 있다.
- **참여자·action 카드:** 키·라벨은 모니터 조건과 같다. 참여자는 보낸·받는 쪽 키에 모두 센다. 카드 값 = 건수(요청 + 응답) · 실패 두 칸(§8-1) · 평균 소요(§7 단계).
  - 정렬 기준: 건수 · 실패 · 평균 소요. 「실패」는 합계(§8-1)로 정렬한다. 기본은 실패 많은 순이다. 같으면 건수 많은 순, 같으면 라벨순이다.
  - 값이 없는 칸(평균 소요 「—」)은 정렬 방향과 관계없이 맨 뒤다. 검색은 §9-1 과 같은 함수다.
- **추이:** 최근 N분(D11)을 1분 칸으로 나눈다. 칸은 브라우저 수신 시각 기준이다(§5 와 같은 시계). 소요는 응답을 받은 칸에 넣는다. 칸마다 평균·최대 소요를 둔다.
  - 집계를 시작하기 전의 칸은 값이 없다. 0 이 아니다. 막대·점을 그리지 않고 표에 「집계 전」으로 적는다.
- **`EVENT` 행(D2(b)).** 기준 구현의 현황판에는 이 종류가 들어온 적이 없다. 아래 규칙은 기준 구현으로 검증되지 않았다.
  - 지표(§8)·방향 줄·참여자·action 카드·보낸 측 규모에는 세지 않는다. 모두 요청·응답 교환을 재는 칸이다.
  - 결과 분포에는 센다. 모니터 결과 패싯(§9)과 같게 송신 배지만이다. 송신 배지가 있으면 비율의 분모에도 든다.
  - 「요청·응답이 아닌 메시지 N건」을 따로 세어 범위 안내 아래에 알린다.
  - 계약 테스트의 메시지열에 `EVENT` 를 섞는다. 모니터 쪽 기대값도 위 칸에서 `EVENT` 를 빼고 낸다.

| 상황 | 기대 |
| - | - |
| 요청 받음 | requests 1 · waiting 1 · 결과 분포 대기 1 |
| 그 요청에 응답 `success=true` | 요청 결과 대기 → 처리 성공. waiting 0 · responses 1. 둘 다 요청 방향 줄 |

## 17. 현황판 링크·차트(선택) — `parseMonitorFilterQuery` · `monitorFilterLink` · `axisTicks` · `chartFrameOf`

**모니터로 가는 링크.** 현황판의 숫자·카드를 누르면 그 조건 하나를 건 모니터가 열린다. 조건은 주소 쿼리로 넘긴다.

- `monitorFilterLink(group, key) → {path, query}`: `path` = 모니터 경로, `query` = `{그룹의 쿼리 이름: key}` 한 쌍. `group` 은 방향·결과·참여자·action 중 하나, `key` 는 §9 그룹 키다. 쿼리 이름은 상수 한 곳에 둔다.
- `parseMonitorFilterQuery(search) → filter`: 주소 쿼리 문자열 → §9 조건.
- 모니터는 쿼리를 **화면을 열 때 한 번만** 읽는다. 연 뒤 조건을 바꿔도 주소는 그대로다. 쿼리가 없으면 기본 조건(전체)이다.
- 방향은 하나만 고르는 조건이라 처음 값만 본다. 결과·참여자·action 은 같은 이름을 여러 번 주면 모두 고른다. 모르는 이름·값은 무시한다. 결과는 보이는 결과 키(§9)만 값으로 알고, 그 전부면 전체로 접는다. 검색어는 쿼리로 받지 않는다.
- 방향 링크의 한계: 모니터의 방향 조건은 메시지 방향이다. 현황판의 방향 줄은 요청 방향 묶음이다(§16). 그래서 링크로 연 목록에는 그 방향으로 보낸 응답도 보이고, 이 줄의 응답은 없다. 이 차이를 설명 popover 에 적는다.

| 쿼리(이름은 예시) | 기대 조건 |
| - | - |
| 없음 | 기본(전체) |
| `direction=OUTBOUND&direction=INBOUND` | 방향 OUTBOUND |
| `direction=UP` | 방향 전체 |
| `result=FAIL&result=NOPE` | 결과 [FAIL] |
| 결과 키 6개 전부 | 결과 [] (전체) |
| 송신 거절 칩 숨김, 나머지 결과 키 5개 전부 | 결과 [] (전체) |
| 송신 거절 칩 숨김, `result=SEND_REJECTED` | 결과 [] (전체) — 보이지 않는 키는 모르는 값이다 |
| `party=` | 참여자 [] (빈 값은 버린다) |
| `action=` | action [「action 미상」 키] |

**차트.** 차트 라이브러리를 쓰지 않는다. 좌표·눈금·선 경로를 순수함수로 내고, 화면은 SVG 로 그리기만 한다.

- `chartFrameOf(width | null) → {width, height, pad: {top, right, bottom, left}}`: 차트의 실제 폭(px)을 재어 viewBox 폭으로 쓴다. 높이·여백은 상수다. 그래서 1 단위 = 1px 이고, 축 글자·선 두께가 창 폭과 관계없이 같다. 재기 전(null)이면 기본 틀이다.
- `axisTicks(max, {integer})`: 눈금 = 0, 간격 배수(최대값과 축 높이의 15% 이상 떨어진 것만), 그리고 실제 최대값. 간격은 1·2·5 × 10ⁿ 중 `max ÷ 목표 칸 수` 이상인 가장 작은 값이다. 건수 축은 정수 간격이다. 최대값보다 큰 "보기 좋은 수"를 만들지 않는다.
- 꺾은선은 이웃한 두 칸에 모두 값이 있을 때만 잇는다. 값이 없는 칸에서 선이 끊긴다.
- 계열은 색만으로 가르지 않는다. 막대는 칸 안 자리, 선은 실선·점선으로 가르고 범례에 글자로 적는다.
- 대체 텍스트는 요약 한 문장이다. 칸별 값은 화면 낭독기용 표로 둔다.
