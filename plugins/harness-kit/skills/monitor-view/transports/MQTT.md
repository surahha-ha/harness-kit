# 전송 부록 — MQTT

MQTT 로 메시지를 주고받는 시스템에서 T1~T12(SKILL.md 「전송 방식 부록」)의 답이다.
답은 출발점이다. 클라이언트 라이브러리·프로토콜 판(3.1.1 · 5)·설정에 따라 다르다. 이 프로젝트 코드로 확인하고 결정 기록에 근거와 함께 적는다.
예시 값은 모두 합성값이다. 토픽 뿌리는 `example` 로 적는다.

## T1. 채널 체계 → D2

- 채널은 토픽이다. 요청·응답은 보통 토픽 끝 조각으로 가른다.
  - 요청: `example/{tenant}/request`
  - 응답: `example/{tenant}/response/{requesterClientId}` — 끝 조각이 요청한 쪽의 clientId 다
- 테넌트는 토픽 조각 하나에 든다. 위 예는 둘째 조각이다. 뽑지 못하면 그 메시지는 버린다.
- 응답이 가는 끝점은 응답 토픽 끝의 clientId 다.
- 요청·응답이 아닌 토픽(알림·상태)이 구독 와일드카드에 함께 걸리는 경우가 많다. D2(a)·(b) 중 하나를 정한다.
- 확인할 것: 토픽 상수·빌더, 구독 패턴(`+`·`#`)

## T2. 상관 키 → D3

- 기준 구현은 봉투 최상위 `requestId` 를 썼다.
- MQTT5 에는 Correlation Data · Response Topic 속성이 있다. 본 처리가 이미 쓸 때만 그것을 읽는다. 모니터 때문에 싣기 시작하지 않는다.
- QoS1 재전송(DUP)은 같은 payload 라 같은 키가 다시 보인다(T7).

## T3. 송신 확인 → D1 · D11

| D1 질문 | MQTT 의 답 |
| - | - |
| 확인 신호 | QoS1 은 PUBACK, QoS2 는 PUBCOMP 가 확인이다. 라이브러리의 송신 완료 콜백에서 받는다. 콜백은 대개 기본으로 있어 설정 변경이 없다. QoS 를 올리는 것은 본 처리 변경이라 승인 대상이다. QoS0 은 확인이 없다. 발행 호출이 예외 없이 끝나면 `SENT` 다 |
| 거절 코드 | MQTT5 의 reason code 0x80 이상이 거절이다 → `REJECTED`. QoS1 은 PUBACK, QoS2 는 PUBREC 에 실린다. 연결 끊김·시간 초과 같은 클라이언트 쪽 오류는 `FAILED` 다. 3.1.1 이거나 QoS0 이면 `REJECTED` 가 생기지 않는다 |
| 확인 지연 | 보통은 브로커 왕복 한 번이다. 상한은 라이브러리의 완료 대기 시간·재전송 간격·keep-alive 가 정한다. 그 설정 키를 D11 근거로 적는다 |
| 오프라인 버퍼 | 클라이언트 라이브러리에 끊긴 동안 발행을 쌓는 버퍼가 있을 수 있다. 켜져 있으면 `NOT_SENT` 를 쓰지 않는다 |
| 동기 응답 흐름 | 없다. 응답은 다른 토픽의 별도 메시지다 |

- A→B 요청 이벤트의 `at` 은 PUBACK 콜백 시각이다. PUBACK 이 늦으면 B 의 응답이 그 요청 이벤트보다 먼저 기록된다. 그래서 D11 「먼저 온 응답 창」이 필요하다.
- 기준 구현은 PUBACK 지연을 재지 않고 창을 10초로 정했다. 브로커 지표나 로그로 지연을 재면 창 길이의 근거가 된다.
- `FAILED` 에는 PUBACK 을 제때 못 받은 경우가 섞인다. 메시지는 실제로 도착했을 수 있다.
- 거절 예(합성): `"sendResult": "REJECTED"` · `"error": "PUBACK reason code 0x87"` · `"channel": "example/tenant-001/response/b-node-7f2a"`

## T4. 상대 ID → D4

- **PUBLISH 패킷에는 발행자 clientId 가 없다.** 브로커만 안다. 구독자는 받은 메시지에서 그것을 읽지 못한다.
- 읽을 수 있는 곳은 셋뿐이다.
  - 봉투(최상위 또는 `data` 안)
  - 토픽 조각(예: 응답 토픽 끝의 요청자 clientId)
  - MQTT5 user property — 본 처리가 이미 싣는 경우만
- 흐름마다 출처가 다르다. 예(합성): B→A 요청 봉투에 clientId 가 없고, A→B 응답 토픽 끝에만 B 단말의 clientId 가 있다. 그러면 B→A 요청의 `senderId` 는 null 이고, 패널은 응답 쪽 ID 로 그 쌍을 묶는다.
- A→B 요청 토픽이 테넌트 단위면 그 테넌트의 B 단말이 모두 받는다. 받는 쪽을 송신 때 특정할 수 없다. `receiverId` 는 null 이고 D12 사유는 「모두 받음」(라벨 `테넌트 전체`)이다.

## T5. 자기 송신 되돌림 → D4

- A 가 요청을 보내는 토픽을 A 도 구독하면(와일드카드 포함) 그 요청이 A 로 돌아온다. 공유 구독이든 아니든 같다.
- 되돌림은 보낸 인스턴스가 아닌 다른 A 인스턴스로 갈 수 있다.
- D4 방법 (d) 에 해당하는 MQTT 옵션은 구독 옵션 **No Local** 이다.
  - MQTT5 에만 있다.
  - 인스턴스 1대 · 비공유 구독일 때만 맞다. 공유 구독에 No Local 을 걸면 프로토콜 오류다.
  - 본 처리 구독 설정을 바꾸는 일이라 사용자 승인을 받는다.
- D4 방법 (c) 는 MQTT5 user property 의 발행자 표식이다.

## T6. 다중 인스턴스 수신 → D9

| 구독 방식 | 같은 메시지를 받는 A 인스턴스 | D9 규칙 |
| - | - | - |
| 공유 구독(`$share/{group}/...`) | 한 대 | 받은 한 대가 기록하고 팬아웃 |
| 인스턴스 전용 토픽(자기 clientId 가 든 응답 토픽) | 한 대 | 받은 한 대가 기록하고 팬아웃 |
| 비공유 구독, 모든 인스턴스가 같은 토픽 | 모두 | D9 (a)(권장) 또는 (b) |
| 비공유 구독, 일부 인스턴스만 그 토픽 | 일부 | D9 (b) |

- `at` 같은 인스턴스 확인: A→B 요청의 응답 토픽을 보낸 인스턴스만 구독하는가. 응답 토픽을 공유 구독·와일드카드로 여러 대가 받으면 다른 인스턴스가 응답을 기록할 수 있다.

## T7. 전달 보장

- QoS1 은 최소 한 번 전달이다. 같은 메시지가 두 번 올 수 있다.
- 세션을 이어 붙이면(clean session 끔) 끊긴 동안의 메시지가 재연결 뒤 다시 온다.
- 수신 기록은 중복 제거 전이라 이 중복이 그대로 보인다. 가이드 「한계」에 적는다.
- 순서: 한 연결·한 토픽·같은 QoS 안에서는 보낸 순서로 온다. 토픽이 다르면 순서를 기대하지 않는다(요청·응답 토픽 사이 등).
- 트랜잭션이 없다. 중단된 트랜잭션의 메시지가 보이는 일은 없다.

## T8. 기록 지점을 거는 자리

- 수신: 라이브러리의 메시지 도착 콜백. 본 처리 핸들러로 넘기기 직전이다.
- 송신: 시도하지 않은 발행(연결 없음)은 발행 호출 자리에서 즉시. 시도한 발행은 송신 완료 콜백(T3)에서.
- 두 자리 모두 콜백 스레드·이벤트 루프에서 온다. 큐에 넣고 즉시 반환한다(SKILL.md 2단계 2).
- 제3 관찰자: 별도 클라이언트로 같은 토픽을 구독할 수 있다. 그 클라이언트는 받기만 보고 발행 결과(PUBACK)는 못 본다(SKILL.md 2단계 1). 와일드카드 구독은 브로커 ACL 이 막을 수 있다.

## T9. MQTT 함정

- **봉투에 clientId 가 있다고 가정했다.** PUBLISH 에는 발행자 ID 가 없다. 봉투에도 없으면 자기 송신 판별·패널 묶음이 막힌다. T4 를 먼저 푼다.
- **비공유 구독인데 INBOUND 를 모두 팬아웃했다.** 모든 인스턴스가 같은 메시지를 받아 각자 버스에 싣는다. 브라우저에 인스턴스 수만큼 겹친다. T6 표로 토픽마다 가른다.
- **공유 구독에 No Local 을 걸었다.** 프로토콜 오류로 구독이 실패한다. 본 처리 수신이 멈춘다. T5 의 조건을 지킨다.
- **PUBACK 을 기다리지 않고 송신 이벤트를 냈다.** QoS1 인데 발행 호출 직후 `SENT` 를 내면 거절·미확인을 놓친다. 완료 콜백에서 낸다. 대신 응답이 먼저 보일 수 있다(T3).
- **오프라인 버퍼가 켜진 줄 몰랐다.** 라이브러리 기본값이 버퍼 켬일 수 있다. 끊긴 동안 `NOT_SENT` 로 기록한 메시지가 재연결 뒤 도착한다. 클라이언트 설정을 확인한다.
- **3.1.1 인데 `REJECTED` 칩을 기대했다.** 3.1.1 PUBACK 에는 reason code 가 없다. 거절은 보이지 않는다. 계약과 가이드에 적는다.
- **모니터 때문에 user property 를 싣기 시작했다.** 본 처리 송신 바이트가 바뀐다. 상대가 그 속성을 모르면 문제가 없어 보여도 계약 변경이다. 이미 싣는 경우만 읽는다.

## T10. 전송 메타데이터 → CONTRACT.md §3 · D6

- 메시지마다 토픽 · QoS · retain 표시 · DUP 표시가 있다. MQTT5 면 user property 도 있다. 파티션·오프셋 같은 위치 값은 없다.
- 토픽은 이미 `channel` 이다. 올릴 후보는 retain 과 user property 정도다. user property 를 올리면 그 키도 대조한다(MASKING.md §4).

## T11. 직렬화 형식 → MASKING.md §1

- payload 는 바이트일 뿐이다. 형식은 본 처리가 정한다(대개 JSON).
- MQTT5 의 payload format indicator · content type 이 있으면 형식 판단에 쓴다. 없으면 본 처리 디코더와 같은 방법으로 읽는다.

## T12. 보낸 시각과 수신 지연 → RULES.md §6

- PUBLISH 에는 보낸 시각이 없다. 봉투에 있을 때만 `sentAt` 을 채운다.
- 세션을 이어 붙이면(T7) 재연결 뒤 끊긴 동안의 메시지가 한꺼번에 온다. 그 `at` 은 재연결 뒤 시각이다.
- retain 메시지는 구독 때 바로 온다. 오래전에 보낸 것이라도 「방금 받음」으로 보인다.
