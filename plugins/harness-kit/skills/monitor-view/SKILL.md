# monitor-view — 시스템 사이에 오가는 메시지를 실시간으로 보는 화면

두 개 이상의 시스템이 메시지·이벤트를 주고받는다. 이 스킬은 그 메시지를 브라우저에서 실시간으로 보는 **모니터 화면**과 그 **사용 가이드**를 만든다.
전송 방식과 스택은 가리지 않는다. 계약·규칙·화면은 전송·언어 중립으로 적었다. 전송 고유의 답은 전송 부록에 있다(아래 「전송 방식 부록」).

모니터는 **관측 전용**이다. 본 처리(송수신·핸들러)의 동작·봉투·채널·직렬화·지연을 하나도 바꾸지 않는다.
모니터가 실패해도 본 처리는 그대로 돈다. 모든 단계의 판정 기준이 이 말이다.

## 용어

| 말 | 뜻 |
| - | - |
| 우리 시스템(A) | 모니터를 붙이는 시스템. 인스턴스가 여럿일 수 있다 |
| 상대(B) | A 와 메시지를 주고받는 시스템. 끝점(단말·인스턴스)이 여럿일 수 있다. 상대 시스템이 둘 이상이면 상대마다 표시 이름을 둔다(D12) |
| 전송 | 메시지를 나르는 수단. 예: MQTT · Kafka · HTTP 웹훅 · WebSocket · 메시지 큐 |
| 채널 | 메시지가 오가는 이름 있는 길. 토픽 · 큐 · 경로 · 이벤트 이름 등 |
| 방향 | `INBOUND` = B→A(A 가 받음) · `OUTBOUND` = A→B(A 가 보냄) |
| 종류 | `REQUEST` · `RESPONSE` · `EVENT`(요청·응답이 아닌 메시지, D2(b)일 때만) |
| 상관 키 | 요청과 응답을 잇는 값(correlation key). 예: `requestId` |
| 짝 | 상관 키가 같은 요청 하나와 응답 하나 |
| 참여자 ID | 메시지를 보내거나 받는 끝점의 식별자. A 인스턴스 ID 와 상대 ID 둘 다다 |
| 송신 확인 시점 | A 의 송신 결과가 정해지는 순간. 예: 브로커 확인 · 전송 응답 · 완료 콜백(D1) |
| 결과 | 행마다 붙는 6종: 처리 성공 · 처리 실패 · 송신 거절 · 송신 실패 · 대기 · 시간 초과 |
| 테넌트 | 보기 범위의 단위(고객사·조직 등). 범위가 하나뿐이면 D5 가 「단일 범위」다 |
| 기록 지점 | A 가 메시지를 받은 직후, A 의 송신 결과가 정해진 직후. 모니터는 이 두 곳에서만 본다 |
| 두 시계 | 브라우저 수신 시각(시간 초과·새 행·활동 판정)과 서버 `at`(소요). 한 판정에 섞지 않는다 |
| 가이드 「한계」 | GUIDE.md §5 의 10절 「알아 둘 한계」. 모든 문서의 「한계」는 이 절이다 |
| 봉투 | payload 의 최상위 구조. 상관 키·action·data 같은 공통 칸을 담는다. A·B 사이의 계약이라 모니터가 바꾸지 않는다 |
| 현황판 | **선택 화면.** 화면을 연 뒤 받은 메시지를 누적해 지표·추이·분포로 보인다(UI.md §14) |
| 기준 구현 | 이 스킬을 뽑아낸 실제 구현 하나. 사례 값·함정의 출처다. 읽는 사람은 볼 수 없다. 그 값을 옮기지 말고 이 프로젝트의 근거를 찾는다 |
| `coordinator` · `ui-ux-guide` | 다른 스킬(있으면 쓴다). 앞은 여러 계층 작업 지휘, 뒤는 화면 작업 절차다. 없으면 BE → 계약 → FE 순서와 검증 계획을 착수 전에 보이고, 화면은 UI.md 와 레포 UI 문서만 따른다 |

## 프로필 — 프로젝트 고유값을 읽는 곳

레포 루트에 `harness.config.mjs` 가 있으면 그 `project` 블록에서 읽는다(슬롯 정의는 harness-kit README 「프로젝트 프로필」). 없으면 아래 질문을 사용자에게 묻는다.
어느 쪽이든 쓴 값을 결정 기록 문서의 「프로필」 절에 적는다.

- 읽는 순서: 현재 레포 config → `project.pairOwner` 가 가리키는 주 레포 config.
  - 짝 공통값(`layout`·`contract`·`git`)은 주 레포에만 있다.
- 이 스킬이 읽는 슬롯: `layout` · `sides.be` · `sides.fe` · `commands.be.testOne` · `commands.fe.testOne` · `commands.fe.devMock` · `contract.rulesDoc` · `docs.uiUxRules` · `risk.devServer`

| - | - | - | - |
| `layout` | `single` = BE·FE 가 한 레포 · `paired` = 두 레포 | 4단계 계약 픽스처 위치 | 「BE 와 FE 가 한 레포에 있나요, 다른 레포인가요?」 |

**부록 고르기**

1. D1 에서 전송을 정한다.
2. `transports/` 에 같은 전송의 부록이 있으면 연다.

- 지금 있는 부록은 [transports/MQTT.md](transports/MQTT.md) 하나다.

## 0단계 — 결정

1. PITFALLS.md §0 을 읽는다. 전송 부록이 있으면 그 T9 도 읽는다.
2. 코드에서 답을 먼저 찾는다. 볼 곳은 DECISIONS.md 각 항목의 「먼저 볼 곳」이다.
   - 찾은 답은 근거(파일·심볼)와 함께 적는다.
3. 코드로 정하지 못한 항목만 묻는다. 한 번에 하나씩, 권장안과 이유를 함께 낸다.
4. D1~D12 뒤에 현황판을 만들지 묻는다(DECISIONS.md 「현황판」). 코드로 정할 수 없는 사용자 결정이다.
   - 결정 한눈 목록은 DECISIONS.md 끝 「결정 기록 양식」의 결정 표다.

**완료 기준:** D1~D12 가 모두 값 또는 「해당 없음 — 이유」를 가진다. T1~T12 의 답이 있다(부록 또는 결정 기록 「전송」 절). 현황판은 있음 / 없음이다. 값마다 근거(코드 위치·사용자 답)가 있다. D6 의 상대 키 목록을 못 받았으면 「미확보」로 적는다. 4단계 게이트가 이것을 다시 막는다.

## 1단계 — 결정 기록 문서

1. DECISIONS.md 끝의 양식으로 레포에 문서 하나를 만든다. 위치는 사용자에게 묻는다(관례: `docs/rules/` 아래 `monitor-view.md` 또는 ADR 한 건).
2. CONTRACT.md 를 이 프로젝트 값으로 채운다. 그 결과를 같은 문서나 `contract.rulesDoc` 에 둔다. 두 곳에 복제하지 않는다.
3. 레포 `CLAUDE.md` 의 작업 라우팅 표에 한 줄을 건다. 그 표가 없으면 레포 README 의 문서 목록에 한 줄을 건다.

**완료 기준:** 문서가 있다. 계약 필드표·이벤트 이름·송신 결과 값·거부 응답표가 프로젝트 값으로 채워졌다. 라우팅 한 줄이 걸렸다.

## 2단계 — BE

PITFALLS.md §2 를 읽는다. 항목마다 관측 전용을 지키는지 본다.

1. **기록 지점 두 곳.** 거는 자리는 T8 이다.
   - 수신: 받은 직후, 중복 제거·검증 전이다. 그래서 재전송·중복 전달(T7)이 그대로 보인다. 이것은 가이드 「한계」에 적는다.
   - 송신: 송신 결과가 정해지는 순간 1건을 낸다. 시도하지 않은 송신은 즉시, 시도한 송신은 송신 확인 시점(D1)에 낸다.
   - 본 처리 코드에 늘어나는 것은 "이벤트 하나 내기"와 그 호출의 실패 격리(예외 삼킴·panic 회수 등)뿐이다.
   - A 가 보낸 메시지가 A 의 수신으로 되돌아오면 수신 기록에서 버린다. 가리는 방법은 D4 다.
   - **제3 관찰자는 기록 지점을 대신하지 못한다.** 본 처리 밖에서 전송을 따로 구독·소비하는 관찰자(T8)는 송신 결과(`REJECTED`·`FAILED`·`NOT_SENT`)를 못 보고, 방향·`receiverId` 를 정할 기준도 없다. 쓰려면 INBOUND 전용으로만 쓰고, 송신 결과 칸이 비는 이유를 계약에 적는다.
2. **유한 큐 — 기록 지점을 막지 않는다.**
   - 리스너는 큐에 넣고 즉시 반환한다. 변환·마스킹·발행은 큐 뒤에서 한다.
   - 큐에 넣기는 막히지 않는다. 가득 차면 기다리지 않고 버린다(예: Go 는 `select … default` 로 보낸다). 종료 중에 닫힌 큐에 넣지 않는다.
   - 큐를 비우는 방식은 프로젝트 런타임에 맞게 고른다. 기준은 「큐를 비우는 일을 본 처리와 다른 실행 단위로 넘길 수 있는가」다(D1).
     - 스레드형: 작업 스레드 하나가 큐를 비운다. 전송 클라이언트의 콜백 스레드·스레드풀에서 일하지 않는다.
     - 경량 스레드형(예: Go goroutine): 전용 작업 단위 하나가 유한 채널을 비운다. 콜백이 본 처리 핸들러 안에서 와도 넘기기만 한다.
     - 이벤트 루프형(넘길 수 없다): 큐만으로는 지연을 막지 못한다.
       - 다음 턴의 매크로태스크로 한 건(또는 작은 묶음)씩 비운다. 예시(Node): `setImmediate`.
       - 마이크로태스크(`Promise.then` 등)로 잇지 않는다. 같은 턴에 다 돌아 본 처리를 막는다.
       - 한 건 처리 시간이 D11 허용치를 넘으면 작업자 스레드·프로세스로 옮긴다. 큰 payload 하나로 잰다.
   - 큐 상한은 작게 둔다(D11). 넘치면 그 메시지는 모니터에서 버린다.
   - 버린 건수를 모아 간격을 두고 WARN 을 1회 남긴다. 버릴 때마다 로그를 남기지 않는다.
   - **작업 흐름의 어떤 실패도 프로세스를 내리지 않는다.** 예외형 언어는 WARN 후 삼킨다. Go 처럼 회수하지 않은 panic 이 프로세스를 내리는 런타임은 작업 단위 안에서 회수한다(`recover`). 작업 단위가 멈추면 큐가 차서 버림으로 이어질 뿐, 본 처리는 그대로다.
3. **이벤트 생성.** CONTRACT.md 필드표대로 만든다.
   - 종류는 D2 규칙으로 판정한다. 요청·응답이 아닌 메시지는 D2 결정대로 처리한다.
   - 테넌트를 뽑지 못한 메시지는 버린다. 보낼 구독자가 없다. D5 가 「단일 범위」면 뽑지 않고 모두 그 범위로 보낸다.
   - 참여자 ID 는 CONTRACT.md §5 표대로 읽는다. 출처는 D4 다. 봉투·채널은 읽기만 한다.
4. **마스킹.** MASKING.md 대로 한다. 팬아웃 전에 한 번 가린다. 원문은 버스·스트림 어디에도 싣지 않는다.
5. **팬아웃(D9).**
   - 버스 메시지는 `{테넌트, 이벤트}` 다. 모든 인스턴스가 받아 자기 연결 중 같은 테넌트에만 보낸다.
   - 브라우저에는 `이벤트` 만 보낸다. 버스 메시지를 그대로 보내지 않는다.
   - 연결의 테넌트는 `connected` 로 한 번 알린다(CONTRACT.md §2). 다른 테넌트의 값은 어느 칸에도 싣지 않는다.
   - 같은 INBOUND 를 여러 인스턴스가 받으면 중복을 막는 규칙은 D9 다.
6. **스트림 엔드포인트(D8).**
   - 인증을 요구한다. 테넌트는 인증 주체에서 연결 때 한 번 푼다. 요청 파라미터로 받지 않는다.
   - 연결 직후 `connected` 를 1회 보낸다. 하트비트를 보낸다.
   - 연결 보관소는 다른 스트림과 분리한다. 키가 다르다.
   - 거부 응답은 CONTRACT.md §7 표의 상태·본문을 쓴다.
7. **플래그(D7).** 전송 전체 플래그(있으면)와 모니터 플래그가 **둘 다** 참일 때만 기록·팬아웃·엔드포인트가 생긴다. 꺼지면 엔드포인트가 없어 404 다. 운영 기본값은 끔이다.

**완료 기준:** 1~7 마다 코드 위치가 있다. 본 처리 쪽 변경이 이벤트 발행 호출과 그 실패 격리뿐이다. 근거로 `git diff --stat` 의 본 처리 파일 목록을 적는다.

## 3단계 — FE

PITFALLS.md §3 을 읽는다.

1. **진입 가드.** 운영 빌드면 진입 때 다른 화면으로 보낸다. 로그인·권한은 앱 공통 가드를 쓴다.
   - **mock 모드가 건너뛰는 것**(이 목록은 여기 한 곳에만 둔다): 로그인·권한 가드, 스트림 연결(모의 피드가 대신한다).
   - 운영 진입 가드는 건너뛰지 않는다. mock 모드는 운영 빌드가 아니라서 원래 통과한다.
2. **스트림 수신(D8·D10).**
   - 상태는 다섯이다: `idle` · `connecting` · `open` · `reconnecting` · `stopped`.
   - 닫힌 연결의 상태를 `classifyStreamProbe`(RULES.md §12)로 판정한다. 상태를 얻는 법은 D8 수단마다 다르다.
     - SSE: 끊기면 브라우저 자동 재연결에 맡긴다. 연결이 닫히면(CLOSED) 같은 URL 에 상태 확인 요청을 1회 보내 그 응답을 넣는다.
     - fetch 스트림: 연결 응답의 상태·본문을 그대로 넣는다. 상태 확인 요청은 보내지 않는다. 재연결은 직접 만들고 지연은 D11 값으로 건다.
     - WebSocket: 연결 전 응답(핸드셰이크)의 상태 또는 닫힘 코드를 같은 입력 꼴로 바꿔 넣는다. 그 대응표를 결정 기록에 적는다.
   - 판정이 재연결이면 정해진 지연 뒤 다시 연다.
   - 401 이면 D10 의 갱신 경로를 먼저 1회 탄다. 그 결과를 판정 입력 `refresh` 로 넘긴다. 갱신이 실패하거나 연속 상한에 닿으면 멈춘다. D10 이 「갱신 없음」이면 바로 멈춘다.
3. **파싱.** `parseMessage` 로 검사한다. 계약 위반 메시지는 버리되, 버린 건수를 개발 콘솔에 남긴다. 조용히 버리지 않는다.
4. **버퍼.** 최신순으로 둔다. 상한은 고를 수 있다(D11). 넘치면 오래된 것부터 버린다. 받은 버퍼와 멈춘 화면 버퍼 둘을 둔다.
5. **판정.** RULES.md 의 함수를 모두 순수함수로 만든다. 컴포넌트는 조립만 한다.
6. **화면.** UI.md 대로 만든다. 보기 3종 · 상세 · 필터 · 지표 · 연결 상태 · 빈 상태 · 테마다.
7. **모의 피드.**
   - mock 모드에서만 동적으로 불러온다. 운영 빌드 경로에 들지 않는다.
   - 계약과 같은 이벤트 이름·`data` 문자열을 수신 핸들러에 그대로 흘린다. 파서를 우회하지 않는다.
   - 첫 묶음에 결과 5종(시간 초과 빼고, D1 이 송신 거절을 없앴으면 4종)이 보이게 과거 시각으로 깐다. 응답이 오지 않는 요청 하나를 넣어 둔다. 시간 초과는 화면을 연 뒤 제한시간(D11)이 지나야 보인다.
   - 첫 묶음(과 `?seed=N`)은 피드를 시작할 때 **동기로** 낸다. 타이머 뒤의 첫 묶음은 가짜 시계를 멈춘 캡처에서 끝내 오지 않는다(GUIDE.md §4).
   - D1 에서 응답이 요청보다 먼저 올 수 있으면, 그런 A→B 쌍을 가끔 섞는다(RULES.md §2).
   - `?seed=N` 은 첫 묶음보다 앞선 과거 시각으로 N건을 먼저 깐다. N 은 버퍼 상한 **선택지의 최댓값**으로 자른다.
   - `?parties=N` 은 상대 ID 총수를 N 으로 늘린다(많은 참여자 눈 검증용). N 은 범위로 자른다. 아래 끝은 첫 묶음이 쓰는 수, 위 끝은 미리 채우기 건수가 감당되는 수다. 없으면 기본 소수이고 출력도 그대로다.
   - 이 쿼리들은 mock 모드에서만 읽는다. 데이터는 전부 합성값이다. PII 모양은 마스킹 결과와 같게 둔다.
   - 피드 시작·스트림 연결은 정리 함수로 되돌릴 수 있게 한다. 두 번 시작해도 한 벌만 흐른다(예: React 개발 모드 StrictMode 는 effect 를 두 번 돌린다).
8. **다시 그리기 줄이기(RULES.md §15).** 1초 재판정 틱마다 목록 전체가 다시 그려지지 않게 한다.
   - 다시 계산한 행·패널·카드는 `reuseUnchangedItems` 로 이전 객체를 다시 쓴다. 항목마다 컴포넌트를 두고, props 참조가 같으면 다시 그리지 않게 한다(프레임워크마다 다르다, RULES.md §15).
   - 숫자 포맷터는 공용 하나를 쓴다.
   - `?parties=N` 으로 수백 참여자를 띄워 틱마다 끊김이 없는지 본다.

**완료 기준:** RULES.md 의 함수가 모두 판정 모듈에 있고, 컴포넌트에 판정 분기가 없다. mock 모드로 띄워 결과 6종(시간 초과는 제한시간 뒤, D1 이 송신 거절을 없앴으면 5종) · 보기 3종(D4 가 패널을 뺐으면 2종) · 연결 상태를 눈으로 봤다. 본 화면을 보고에 적는다.

**완료 기준:** mock 모드로 두 화면을 오가며 머리가 튀지 않음 · 숫자 링크가 그 조건의 모니터를 엶 · 창 폭을 바꿔도 축 글자 크기가 같음을 눈으로 봤다. 본 화면을 보고에 적는다.

- BE 테스트: 고정 입력으로 이벤트를 만들고 직렬화해 픽스처와 비교한다. 파싱한 값으로 비교한다(키 순서 무관). `id`·`at` 은 테스트가 고정값을 주입한다.
- FE 테스트: 같은 픽스처를 `parseMessage` 에 넣고 필드마다 비교한다.

- 두 레포(`layout: paired`): 계약 문서가 있는 레포가 정본을 둔다. 다른 레포에 같은 이름의 사본을 둔다.
  - 사본 디렉토리에 정본 레포·경로·커밋을 적은 메모 파일을 둔다.
  - 계약이 바뀌면 같은 변경에서 정본과 사본을 함께 고친다. 메모의 커밋이 정본 최신과 다르면 계약 행은 「미확인」이다.

**완료 기준:** 행마다 실행 명령 · 종료코드 · 결과가 있다. 못 돌린 행은 「미확인」으로 남은 레드에 둔다.

## 5단계 — 사용 가이드

PITFALLS.md §5 를 읽는다. GUIDE.md 대로 한다.

1. 사실 시트를 먼저 쓴다. 화면·규칙·마스킹·연결 상태·한계를 코드 근거와 함께 적는다.
2. 모의 피드·가짜 시계·seed 난수·화면 설정 미리 넣기로 GUIDE.md §3 의 장면을 찍는다.
3. 가이드 문서 1장을 10절로 쓴다(현황판이 있으면 11절). 문구는 화면 원문을 상수에서 옮긴다.

**완료 기준:** GUIDE.md 「게시 전 확인」을 모두 통과했다.

## 6단계 — 완료 체크

- [ ] 결정 기록 문서에 프로필 값 · D1~D12 · T1~T12 의 답 · 현황판 있음/없음과 그 근거가 있다
- [ ] 계약이 한 곳에만 있고, BE·FE 가 같은 이벤트 이름·필드를 쓴다
- [ ] 본 처리 diff 가 이벤트 발행 호출과 그 실패 격리뿐이다
- [ ] 리스너가 즉시 반환하고, 큐가 유한하고, 넘침이 WARN 으로 모여 남는다. 작업 흐름의 실패가 프로세스를 내리지 않는다
- [ ] 자기 송신 되돌림을 D4 방법으로 버린다. 여러 인스턴스가 같은 INBOUND 를 받아도 브라우저에 한 번만 보인다(D9)
- [ ] 마스킹이 팬아웃 전에 한 번 돈다. 상대 키 목록과 대조했다(또는 「미확보」로 실고객 데이터 환경에서 끔)
- [ ] 테넌트는 인증 주체에서만 정한다. 플래그 + FE 진입 가드로 운영에서 꺼진다
- [ ] 401 에 D10 갱신 경로가 있다(또는 「갱신 없음」을 가이드 한계에 적었다)
- [ ] 요청·응답이 아닌 메시지의 처리가 계약에 있고, FE 파서가 계약 밖 값을 조용히 버리지 않는다(버린 건수를 남긴다)
- [ ] 시간 초과는 브라우저 시계, 소요는 서버 `at` 이다. 버스가 같은 테넌트 이벤트의 기록 순서를 지킨다(D9)
- [ ] 응답이 요청보다 먼저 와도 창 안이면 짝이 맺힌다. 판정 순서 함수 하나를 모니터·현황판이 함께 부른다
- [ ] 1초 틱에 바뀐 항목만 다시 그린다(수백 참여자 모의 피드로 확인)
- [ ] 현황판을 만들었으면: 수신부·판정을 모니터와 함께 쓰고, 숫자 링크가 그 조건의 모니터를 연다. 안 만들었으면 결정 기록에 「현황판 없음」
- [ ] 4단계 표의 행마다 근거가 있다
- [ ] 가이드가 게시 전 확인을 통과했다
