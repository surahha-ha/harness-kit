# Plugin Sync — 플러그인 최신화

플러그인은 **팀 전체가 따르는 작업 규율**이라, 낡은 채로 방치되면 전원이 같은 방식으로 틀립니다. 이 스킬은 그 낡음(**드리프트**)을 걷어내는 한 사이클입니다. 공용 플러그인 자기 갱신과 프로젝트 오버레이 플러그인 갱신을 같은 절차로 다룹니다.

**정본(SSOT)** 은 `plugin.canonicalRepo` 레포 `plugin.canonicalBranch` 브랜치의 `plugin.dir`. 여기서 고쳐야 팀에 반영됩니다.

## 0. 프로필 — 프로젝트 고유값을 읽는 곳

이 스킬은 프로젝트 고유값을 본문에 갖지 않는다. 정본 레포 루트 `harness.config.mjs` 의 `project` 블록에서 읽는다(슬롯 정의는 harness-kit README 「프로젝트 프로필」).

- 이 스킬이 읽는 슬롯: `plugin.canonicalRepo` · `plugin.canonicalBranch` · `plugin.dir` · `plugin.marketplaceFile` · `plugin.readme` · `plugin.mirrorScript` · `plugin.hookTests` · `plugin.auditSources` · `git.commitExecution`
- **값이 없으면 지어내지 않는다.** 파일이 없거나 슬롯 키가 없으면 그 자리에서 멈추고 사용자에게 묻는다 — 정본 브랜치를 `main`·`develop` 같은 흔한 이름으로 추측하지 않는다. `null` 은 "해당 없음으로 판단됨"이므로 그 단계를 건너뛰고 보고에 적는다(예: `plugin.mirrorScript: null` → 생성물 미러가 없다).

## 1. 정본 작업공간 확보

메인 트리는 다른 작업(미커밋 변경·미푸시 커밋)이 올라가 있는 경우가 많아 그대로 편집하면 남의 변경이 섞이거나 엉뚱한 브랜치에 커밋됩니다. **항상 `origin/<canonicalBranch>` 에서 워크트리를 따로 띄운다.** 큰 수정은 그 위에 별도 브랜치를 만들어 작업한다.

```bash
cd <plugin.canonicalRepo>
git rev-parse --abbrev-ref HEAD          # 지금 어느 브랜치인지 먼저 확정
git fetch origin
git worktree add ../<플러그인명>-wt origin/<canonicalBranch> --detach
# 큰 수정이면: cd ../<플러그인명>-wt && git switch -c chore/plugin-<주제>
```

**완료 기준**: `../<플러그인명>-wt/<plugin.dir>/` 가 존재하고, 그 워크트리 HEAD 가 `origin/<canonicalBranch>`(또는 그 위에서 딴 작업 브랜치)임을 실제 명령으로 확인했다.

> 훅·설정까지 통째로 옮기는 이전(移轉) 브랜치를 정본 브랜치에 **직접 머지하지 않는다**. 그런 브랜치는 라이브 `.claude/hooks/`·`settings.json` 을 지울 수 있다. 편입이 필요하면 정본에서 분기해 **더하기만 하는(가산)** 방식으로 한다.

## 2. 드리프트 감사

`harness-kit:plugin-curator` 에이전트에 위임합니다(감사 소스 매트릭스 A~F·판정 규칙·산출 형식은 그 에이전트가 보유). 에이전트를 쓸 수 없으면 같은 매트릭스를 직접 훑습니다.

위임 시 반드시 넘길 것: **워크트리 절대경로**, 직전 갱신 시점(마지막 커밋, 매니페스트에 `version` 이 있으면 그 값도), `plugin.auditSources`, 이번에 특별히 의심되는 영역(사용자가 말한 것).

**완료 기준**: 여섯 축(A~F) 각각에 대해 "드리프트 N건" 또는 "이상 없음"이 명시된 리포트를 손에 넣었다. 축 하나라도 언급이 없으면 감사는 끝나지 않았다.

## 3. 승인 게이트

리포트를 **위험도순 표 그대로** 사용자에게 제시하고, 항목별로 적용/보류를 받습니다. 판단이 갈리는 항목은 근거를 함께 보여 사용자가 고르게 합니다.

**완료 기준**: 적용할 항목 집합이 사용자 응답으로 확정됐다. 승인 없이 파일을 고치지 않는다.

## 4. 적용

승인된 항목만 반영합니다. 이식 규칙:

- **고치는 곳은 이 플러그인뿐이다.** 플러그인에서 찍어 내린 생성물(레포 `.claude/` 사본, 개인 전역 사본)은 직접 고치지 않는다. 반영이 끝나면 `plugin.mirrorScript` 로 찍어 내린다(`null` 이면 생성물이 없다)
- **생성물에 절대경로를 되살리지 않는다.** 상대 레포 위치는 각 레포 `CLAUDE.md` 나 프로필이 이미 알려주므로 자산 본문은 상대명으로 쓴다 — 그래야 정본과 생성물이 바이트 동일해지고 내용 대조가 오탐 없이 성립한다
- 메모리에서 온 사실은 옮기기 전에 **현행 코드로 재확인**한다. 메모리는 시점 관찰이라 이미 뒤집혔을 수 있다
- 개인 메모리 위키링크(`[[...]]`)는 **내용을 인라인**한다 — 팀원 환경엔 그 메모리가 없어 깨진 링크가 된다
- 문서 규약: 코드값을 문서에 복제하지 말고 **위치(`파일:심볼`)** 로 가리킨다. 라인번호는 쓰지 않는다
- 새 자산을 추가했다면 **미러 범위**를 정한다 — 기본은 플러그인 전용이다. 전역에 두는 것은 프로젝트 중립이면서 전역 규칙이 경로로 가리키는 것뿐이다. 목록의 SSOT 는 `plugin.mirrorScript` 다. 프로젝트 특화 스킬은 전역에 두지 않는다(그 프로젝트 밖에서 오지시가 된다). 플러그인과 같은 내용의 전역 사본은 만들지 않는다 — 설명문이 매 호출 두 번 실린다
- **공용 플러그인에는 프로젝트 고유값을 넣지 않는다.** 경로·명령·호스트·식별자는 프로필 슬롯 참조로 쓴다. 커밋 전에 금칙어 스캔을 돌린다(공용 레포는 `node tools/scan-forbidden.mjs --all`)

**완료 기준**: 승인 목록의 모든 항목이 반영됐고, 반영하지 않기로 한 항목이 무엇인지 말할 수 있다. 그리고 `plugin.mirrorScript` 가 있으면 그 대조 모드가 그린이다.

## 5. 매니페스트 정합

자산을 늘리거나 줄였으면 **세 곳을 함께** 갱신합니다. 하나라도 빠지면 설치자가 받는 설명이 틀립니다.

| 파일 | 갱신할 것 |
|------|-----------|
| `plugin.readme` | 구성표의 **개수**(에이전트 N·스킬 N·커맨드 N·훅 N)와 "언제 쓰나" 목록 행 |
| `<plugin.dir>/.claude-plugin/plugin.json` | `version` — **있을 때만** (아래 분기) |
| `plugin.marketplaceFile` 의 이 플러그인 항목 | 같은 `version` — **있을 때만** |

`version` 을 올릴지는 대상 플러그인의 두 매니페스트(`plugin.json` 과 마켓플레이스 항목)를 **먼저 열어 보고** 가른다.

- **둘 다 `version` 이 있다(명시 버전)** — 둘을 항상 같이 올린다. 자산 추가·절차 변경이면 minor, 오타·문구 정리면 patch. 이 방식에서는 **버전이 바뀌어야 설치본이 갱신된다** — 내용만 바꾸고 버전을 그대로 두면 설치한 사람은 옛 판을 계속 쓴다.
- **둘 다 `version` 이 없다(커밋 SHA 추적)** — 올리지 않고, `version` 을 새로 넣지도 않는다. 설치본은 정본 브랜치의 커밋 SHA 로 판을 가르므로 **정본 브랜치 병합이 곧 배포**다. autoUpdate 가 켜진 곳에 바로 퍼지니, 6단계 검증은 병합 **전에** 끝낸다. `claude plugin validate` 의 version 없음 경고는 이 방식에서 의도된 것이다.
- **한쪽에만 있다** — 고치지 말고 멈춰서 사용자에게 묻는다. 어느 정책이 맞는지는 이 스킬이 정할 수 없다(README·CHANGELOG 의 업데이트 정책을 근거로 보여 준다).

**완료 기준**: 실제 파일 수를 세어 README 개수표와 대조했고, 두 매니페스트의 `version` 이 **둘 다 같은 문자열이거나 둘 다 없다.**

## 6. 검증

- 훅을 건드렸다면 `plugin.hookTests` 의 테스트 — **전건 통과**여야 한다(`null` 이면 훅이 없다)
- `claude plugin validate <plugin.dir>` 와 마켓플레이스 루트 validate — 종료코드 0. 명시 버전이면 `--strict` 를 붙여 경고 0 까지 본다. 커밋 SHA 추적이면 `--strict` 는 version 없음 경고 때문에 반드시 실패하므로 붙이지 않고, 경고가 그 1건(마켓 루트는 그 플러그인 항목 1건)뿐인지 눈으로 확인한다
- 새/수정 스킬·에이전트의 frontmatter 가 파싱되는지: `name`·`description` 존재, `---` 짝 맞음
- `git status` 로 의도한 파일만 변경됐는지 (워크트리라 다른 브랜치 파일이 섞이지 않았는지)

**완료 기준**: 위 넷이 모두 통과했고, 실패한 것이 있다면 고쳐서 다시 통과시켰다.

## 7. 배포·정리

커밋·푸시는 **사용자 확인 후**에 합니다. 커밋은 **고른 경로만 경로 지정으로** 한다.

> 🔴 **`git add <경로>` + 경로 없는 `git commit` 을 쓰지 않는다.** 경로 없는 커밋은 index 전체를 커밋해, 같은 트리에 다른 세션이 stage 해 둔 변경까지 딸려 들어간다. `git add -A`·`git add .` 도 금지다.

1. **커밋 경로**(`<PATHS>`)를 정한다 — 6단계 `git status` 에서 의도한 파일로 확인한 `plugin.dir` 아래 변경 파일과 `plugin.marketplaceFile`. 디렉토리를 통째로 넘기지 말고 파일로 편다(그 아래 남의 변경이 섞인다).
2. 메시지를 임시 파일로 쓰고 사용자에게 확인받는다.
3. `git.commitExecution` 에 따라:
   - `'auto'` — 아래 명령을 **한 번에** 실행한다. 브랜치·toplevel 조건과 커밋이 같은 명령에 있어야 확인과 커밋 사이에 브랜치가 바뀌어도 엉뚱한 곳에 커밋하지 않는다.
   - `'message-only'` — 메시지와 아래 명령을 건네고 실행하지 않는다(푸시도 하지 않는다). 여기서 보고로 간다.
   - 키가 없거나 두 값 밖이면 지어내지 않고 멈추고 묻는다.

```bash
# <WT>=작업 worktree 절대경로(../<플러그인명>-wt) · <BRANCH>=그 worktree 의 작업 브랜치 · <MSG>=메시지 파일
# <NEW…>=커밋 경로 중 미추적 파일(없으면 그 줄을 뺀다) · <PATHS…>=커밋 경로 전부
R="<WT>"; B="<BRANCH>"
[ "$(git -C "$R" rev-parse --show-toplevel)" = "$R" ] \
  && [ "$(git -C "$R" rev-parse --abbrev-ref HEAD)" = "$B" ] \
  && [ ! -e "$(git -C "$R" rev-parse --path-format=absolute --git-path index.lock)" ] \
  && git -C "$R" add -N -- <NEW…> \
  && git -C "$R" commit -F "<MSG>" -- <PATHS…>
```

- 커밋 직후 `git -C "$R" show --stat HEAD` 의 파일 목록이 `<PATHS>` 와 같은지 본다.
- 경로 중 하나라도 git 이 모르는 경로면 커밋 전체가 실패한다 — 실패 메시지의 경로를 고쳐 다시 돌린다(일부만 커밋되지 않는다).

4. 푸시 — 원격과 브랜치를 늘 명시한다. 맨 `git push` 는 upstream 설정에 따라 다른 브랜치를 밀 수 있다.

```bash
# 작은 수정: 작업 브랜치를 정본 브랜치로 바로. non-fast-forward 면 force 말고 fetch 후 다시 얹는다
[ "$(git -C "$R" rev-parse --abbrev-ref HEAD)" = "$B" ] && git -C "$R" push origin "$B:<plugin.canonicalBranch>"
# 큰 수정: 작업 브랜치만 push 하고 정본 반영(MR/PR)은 사용자가 한다
[ "$(git -C "$R" rev-parse --abbrev-ref HEAD)" = "$B" ] && git -C "$R" push -u origin "$B"
```

- `--force` 류는 이 스킬이 쓰지 않는다. `HEAD:` 대신 브랜치 이름을 적는 것은, 조건을 지난 뒤 HEAD 가 바뀌어도 미는 대상이 달라지지 않게 하려는 것이다.

5. 정리 — `git -C <plugin.canonicalRepo> worktree remove <WT>`

설치본 갱신은 사용자가 실행: `/plugin marketplace update <마켓플레이스명>` → `/plugin install <플러그인명>@<마켓플레이스명>` 또는 `/reload-plugins`.

> **캐시 함정**: 마켓플레이스 source 가 directory 타입이면 그 디렉토리의 **현재 체크아웃된 브랜치판**을 받는다. 그 워킹트리가 정본 브랜치보다 뒤처진 브랜치에 있으면 갱신해도 그 브랜치의 옛 버전을 받는다. 갱신 시점엔 정본과 같거나 앞선 브랜치가 체크아웃돼 있어야 한다. 팀 배포는 git 소스(+ 태그 ref)가 이 함정을 피한다.

**완료 기준**: 무엇을 커밋했고 사용자가 무엇을 실행해야 하는지 한 화면으로 보고했다. 워크트리는 제거했거나, 남긴 이유를 말했다.

## 사이클 밖 후속

이 스킬은 **플러그인 사본**만 책임집니다. 감사 중 전역 `~/.claude` 본이나 라이브 `.claude/` 본이 낡은 것을 발견하면, 그건 이 사이클에서 고치지 말고 **별도 항목으로 보고**합니다 — 소유자가 다르고, 섞으면 어느 쪽이 정본인지 흐려집니다.
