# Coordinator — 다계층 작업 오케스트레이션

당신(메인 Claude)이 **지휘자**입니다. 이 스킬은 하나의 기능/변경을 계층별로 쪼개 **올바른 전문가에게 올바른 순서로** 위임하고, 계층 사이의 계약·검증을 책임지게 합니다.

> **왜 메인이 지휘하나**: 서브에이전트는 다른 서브에이전트를 재호출할 수 없다. 실제 위임(Agent 툴 호출)은 **메인 Claude 또는 fork만** 가능하므로, 코디네이터는 서브에이전트가 아니라 **메인이 따르는 플레이북**이다.

## 0. 프로필 — 프로젝트 고유값을 읽는 곳

이 스킬은 프로젝트 고유값을 본문에 갖지 않는다. 레포 루트 `harness.config.mjs` 의 `project` 블록에서 읽는다(슬롯 정의는 harness-kit README 「프로젝트 프로필」).

- 읽는 순서: 현재 레포 config → `project.pairOwner` 가 가리키는 주 레포 config. 짝 공통값(`layout`·`contract`·`git`)은 주 레포에만 있다.
- 이 스킬이 읽는 슬롯: `layout` · `repos.peers` · `sides` · `contract.*` · `data.schemaProcedureSkill` · `data.migrationOverlaySkill` · `risk.destructive` · `agents`
- **값이 없으면 지어내지 않는다.** 파일이 없거나 슬롯 키가 없으면 그 자리에서 멈추고 사용자에게 묻는다 — 다른 프로젝트의 값이나 흔한 기본값으로 채우지 않는다. `null` 은 "해당 없음으로 판단됨"이므로 그 단계를 건너뛰고 리포트에 적는다.

## 1. 접수 & 분해 (항상 먼저)

작업을 받으면 **바로 위임하지 말고** 먼저 어느 계층에 걸치는지 판정한다.

- **스코프 스캔**: DB 스키마 / BE / FE / 테스트 / 마이그레이션 / 문서 중 무엇이 닿는가. 계층의 위치는 `sides`, 짝 레포는 `repos.peers` 로 확인한다.
- **불확실하면 확인**: 계약(필드·endpoint·enum)이나 DB 변경 여부가 애매하면 착수 전에 사용자에게 1~2개만 되묻는다. (설계가 안 정해진 상태 = `agents.schemaDesign` 영역)
- **실행 계획 제시**: 어느 계층을 어떤 순서로, 누구에게 맡길지 **한 번 요약**하고 진행. 큰 변경이면 사용자 승인을 받는다.
- **DDL·데이터 변경이 포함되면 적용 범위를 착수 시점에 합의**: 산출물(파일)만 만들지, 실제 스키마까지 적용할지를 먼저 정한다. "산출물만" 모드면 런타임(실 INSERT/조회)은 **미검증** 상태임을 리포트에 명시하고, `risk.destructive` 에 적힌 명령·운영 ALTER 등 파괴적 적용은 별도 승인. (끝에서야 "런타임 미검증"이 드러나지 않게 처음에 못박는다)

## 2. 라우팅 표 (누구에게 맡기나)

역할 → 에이전트 이름은 `agents` 슬롯이 덮어쓸 수 있다. 덮어쓰기가 없으면 아래 기본 이름을 쓴다. 기본 이름이 "없음"인 역할은 프로젝트 오버레이가 제공해야 하며, 슬롯이 비어 있으면 사용자에게 어떻게 처리할지 묻는다.

| 작업 성격 | 역할 키 → 기본 담당 | 비고 |
|---|---|---|
| DB 변경 필요성이 **아직 미확정** — 분석·설계부터 | `schemaDesign` → 없음(오버레이) | 설계 확정 후 산출물까지 직접 완료하는 에이전트를 둔다 |
| 스키마가 **이미 확정**, DDL 산출물만 기계적으로 | `schemaApply` → 없음(오버레이) | `data.schemaProcedureSkill` 절차 |
| 데이터 **있는** DB(stage/prod) 스키마 이행 / 타 서비스 ETL | `migration` → `harness-kit:data-migration-engineer` | `harness-kit:data-migration`(범용) + `data.migrationOverlaySkill`(프로젝트) |
| BE 구현 | `backend` → `harness-kit:backend-engineer` | 위임이 기본. 메인이 직접 고치지 않는다 |
| FE 구현 / **BE→FE 계약 동기화** | `frontend` → `harness-kit:frontend-engineer` | 짝 레포면 그 레포의 컨텍스트를 연다 |
| 테스트 **작성/유지** (단위·e2e) | `testAuthor` → `harness-kit:unit-test-engineer` | |
| 빌드·lint·기존 스위트 **실행**·diff 리뷰·그린판정·baseline 실측 | `verifier` → `harness-kit:change-verifier` | 작성 아님, 판정 게이트 |
| 넓은 코드 탐색 (다수 파일 훑기) | `Explore` | 결론만 회수 |
| 커밋→푸시 | `/harness-kit:save` | 사용자 요청 시에만 |

**위임이 기본이다** — 메인 컨텍스트는 판단·리뷰·사용자 대화만 하고, 파일을 읽고 고치고 돌리는 일은 서브에이전트에 맡긴다. 세션 성장이 비용의 대부분을 차지하므로, 위임을 기본으로 두면 세션당 비용이 준다.

**독립 작업은 한 메시지에서 병렬로** 위임한다(예: 서로 다른 Controller 2개, 혹은 BE 스펙 정리와 무관한 FE 조사).

**결과 계약을 프롬프트에 박는다** — 위임마다 「결론 · 변경(또는 발견) 파일 목록 · 남은 레드만, 5KB 이내. 전문·로그·스크립트는 scratchpad 파일로 남기고 경로만」 한 줄을 넣는다. 계약 없는 위임 결과는 9~14KB 로 돌아와 메인 컨텍스트가 도로 자란다(계약을 건 결과는 5~8KB).

## 3. 표준 파이프라인 (풀 오케스트레이션)

의존성이 있는 계층은 **순차**, 없는 건 **병렬**. 각 단계는 게이트를 통과해야 다음으로 간다.

```
접수·분해 (§1)
  │
  ├─[DB 변경 있음]→ schemaDesign(설계미정) 또는 schemaApply(확정)
  │                   └ 데이터 보존 필요 → migration
  │                        ↓ (스키마 산출물·적용 완료가 BE의 선행조건)
  ├─ BE 구현 (backend)
  │     └ 계약 변경분(contract.beGlobs 에 걸리는 파일 · endpoint · enum)을 API 스펙으로 정리 ★
  │                        ↓ (BE 계약이 FE의 SSOT)
  ├─ FE 동기화 (frontend) — BE 스펙을 받아 contract.feDirs · contract.feMocks · 컴포넌트 정합
  │                        ↓
  ├─ 테스트 작성 (testAuthor) — 회귀 방지 시나리오
  │                        ↓
  └─ 검증 게이트 (verifier) — build·lint·기존스위트·diff리뷰 → 그린 판정
                           ↓
                        리포트 (§5) → [요청 시] /harness-kit:save
```

`layout` 이 `single` 이고 계층이 하나뿐이면 계약 동기화 단계는 "해당 없음"으로 통과하고 리포트에 적는다.

### 크로스스택 계약 규칙 (절대)
BE 와 FE 가 **하나의 서비스를 나눈 것**이면 API 계약이 공유 자원이다. 계약 규율의 본문은 `contract.rulesDoc` 이 SSOT 다.
- `contract.beGlobs` 에 걸리는 요청/응답 DTO 필드·타입, endpoint URL·method, 상태코드·enum을 바꾸면 **FE 동반 수정이 필수**다.
- BE 단계 산출물에 **반드시 "FE 영향" 항목**(바뀐 endpoint + 요청/응답 JSON 예시)을 남기고, 그걸 SSOT로 `frontend` 역할에 넘긴다.
- 필드 rename 누락은 **빌드는 통과하고 런타임에만 터진다** → FE 정합을 건너뛰지 않는다.
- "이거 어디서 조회/호출돼?" 류 동작 확인은 FE·BE를 **함께** 추적한다(`harness-kit:fe-be-trace` 스킬).

## 4. 게이트 & 되돌림

- **각 단계 실패 = 다음 단계 중단.** verifier 가 레드면 원인 계층으로 되돌려 재위임(회귀 vs 원래 결함 구분은 baseline 실측으로).
- **DDL/데이터 이행은 파괴적** → `risk.destructive` 의 명령·운영 ALTER 등은 사용자 승인 없이 실행하지 않는다.
- 서브에이전트가 `null`(중도 스킵/사망)로 돌아오면 그 계층을 다시 태운다.

## 5. 리포트 (마무리)

지휘자로서 조각을 모아 **하나로** 보고한다:
1. **무엇을 했나** — 계층별(DB/BE/FE/테스트) 변경 요약
2. **계약 매핑** — BE 어느 변경 ↔ FE 어디에 반영
3. **검증 결과** — build/lint/test 그린 여부, 남은 레드
4. **눈 검증 필요분** — 화면 확인이 필요한 항목
5. **다음 단계** — 미완/후속(커밋·e2e·문서 등)
6. **부수 안내** — 이번 작업과 무관한 미추적 변경(`.claude/` 스킬 파일, 기존 `??` 산출물 등)이 워킹트리에 섞여 있으면 커밋 스테이징에서 **분리**하도록 짚는다. (되돌리기 요청 시엔 시작 시점에 이미 있던 변경/파일을 건드리지 않도록 겹침 파일을 가려낸다)

## 6. 언제 쓰지 않나

- 단일 계층 단발 작업(파일 하나 수정, 단순 질문) → 코디네이터 없이 단일 스킬/에이전트로 처리. 단 파일을 읽고 고치고 돌리는 일은 이때도 서브에이전트에 위임한다.
- 이미 정형화된 단일 워크플로우가 있으면 그 스킬을 바로 쓴다: 스키마만=`data.schemaProcedureSkill`, 마이그레이션만=`harness-kit:data-migration`, 구현→e2e→리포트 품질사이클=`harness-kit:qa-cycle`, 저장=`/harness-kit:save`.
- 코디네이터는 이들을 **엮어야 할 때**의 상위 지휘 계층이다.
