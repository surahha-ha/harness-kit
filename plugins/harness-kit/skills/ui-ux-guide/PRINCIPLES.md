# UI 디자인 7원칙 — 뜻·적용·점검·흔한 실패

> 출처: Figma 리소스 라이브러리 「필수 UI 디자인 원칙 7가지 + 그 사용 방법」
> (https://www.figma.com/ko-kr/resource-library/ui-design-principles/). 원칙과 근거는 그 문서를 따른다.
> **적용법·점검 질문·흔한 실패**는 실제 제품에서 난 일을 기준으로 다시 썼다.
> 어느 단계에서 쓰는지는 [SKILL.md](SKILL.md) 의 Stage 번호로 표시했다.

원칙이 있는 이유는 넷이다.

| 이유 | 원칙이 하는 일 |
| - | - |
| 사용성 | 표지판처럼 안내한다 |
| 의사결정 | 고민을 틀에 넣는다 |
| 효율 | 디자인 시스템을 쓰면 같은 과업이 빨라진다 |
| 인지 부하 | 사용자가 기억하고 추론할 양을 줄인다 |

원칙끼리 부딪히면 **인지 부하가 덜한 쪽**을 고른다.

---

## 1. 계층 (Hierarchy) — Stage 2

**뜻.** 화면에서 무엇을 먼저 보고 무엇을 나중에 보는지를 설계자가 정한다. 정하지 않으면 사용자가 정하는데, 그 순서는 매번 다르다.

**적용.**
- 글꼴 크기·굵기, 대비, 여백 세 가지로 순서를 만든다. 색만으로 만들지 않는다.
- 첫 화면(스크롤 전)에는 결정에 필요한 것만 둔다. 스크롤 아래는 "내려가도 되는 정보"다.
- 밀도가 높은 화면(일정표·표)은 계층을 크기 대신 **정렬과 그룹 간격**으로 낸다.

**점검.** 이 화면을 처음 본 사람이 1초 뒤 어디를 보고 있나. 그것이 내가 의도한 곳인가.

**흔한 실패.** 중요한 것을 전부 굵게 하면, 아무것도 굵지 않은 것과 같다. 헤더 뱃지가 본문보다 눈에 띄면, 뱃지가 오표기될 때 화면 전체가 틀려 보인다.

## 2. 점진적 공개 (Progressive disclosure) — Stage 1

**뜻.** 여러 단계의 과업을 한 번에 다 보여주지 않고, 지금 결정할 것만 보여준다. 기능이 많을수록 우선순위가 필요하다.

**적용.**
- 한 화면에서는 한 가지만 결정한다. 온보딩·등록·설정처럼 입력이 많은 과업은 단계로 자른다.
- **진행 표시**로 남은 단계를 알린다. 어디까지 왔는지 모르면 사용자는 중간에 포기한다.
- 기본값과 템플릿으로 흔한 과업은 설정 없이 끝나게 한다. 고급 옵션은 접어 둔다.
- 속성 패널은 선택된 것의 속성만 보인다.

**점검.** 이 단계에서 사용자가 결정해야 하는 것이 정확히 하나인가. 지금 안 쓰는 옵션이 눈에 들어오나.

**흔한 실패.** 접어 둔 정보를 사용자가 찾지 못한다. 접는 것은 "가끔 쓰는 것"이지 "중요하지만 복잡한 것"이 아니다. 반대로 레포가 "항상 보여야 한다"고 정한 정보가 있다(예: 일정표의 모든 일정). 그런 정보를 접으면 사용자가 존재 자체를 놓친다. 그런 정보는 접지 말고 밀도로 푼다.

## 3. 일관성 (Consistency) — Stage 3

**뜻.** 같은 뜻은 제품 전체에서 같은 모양·같은 자리·같은 말이다. 첫 클릭부터 익숙해야 사용자가 과업에 집중한다.

**적용.**
- 공통 컴포넌트·디자인 토큰·용어 사전을 먼저 보고, 있는 것을 쓴다.
- 새 패턴은 **등록한 뒤 쓴다**. 왜 기존 것으로 안 되는지 한 줄을 남긴다.
- 한 단어에는 한 뜻만, 한 뜻에는 한 단어만 쓴다.
  - 어떤 이름도 다른 이름을 포함하지 않는다.
  - 예: "자르기" 와 "잘라내기" 가 함께 있으면 둘 다 틀린 것이다.
- 같은 결과를 내는 세 경로(버튼·닫기·단축키)는 같은 확인 절차를 거친다.

**점검.** 이 버튼과 같은 일을 하는 버튼이 다른 화면에 있나. 모양·말·자리가 같은가.

**흔한 실패.** 같은 판정을 두 화면에 각각 구현하고 한쪽만 고친다. 그러면 보기와 설정이 같은 날 다르게 보인다. 이것은 UI 문제이기 전에 공통화 문제다(레포 규칙에 공통화 절이 있으면 그것을 따른다).

## 4. 대비 (Contrast) — Stage 3

**뜻.** 중요한 것으로 시선을 끈다. 강조는 희소해야 강조다.

**적용.**
- 주 행동 하나만 채운 색으로 둔다. 나머지는 윤곽선이나 텍스트 버튼으로 둔다.
- 파괴적 행동(삭제·취소·초기화)은 색·위치·확인 절차 중 **둘 이상**으로 구분한다. 색 하나로는 색약 사용자에게 구분이 없다.
- 상태색은 레포가 정한 팔레트 안에서만 쓴다. 상태가 늘어도 색을 늘리지 않는다.

**점검.** 화면에서 채운 색 버튼이 몇 개인가. 하나가 아니면 이유가 있는가.

**흔한 실패.** 경고색을 정보 표시에도 써서 진짜 경고가 묻힌다. "계정 삭제" 를 빨강으로, "계정 유지" 를 회색으로 두는 것은 좋은 대비다. 둘 다 빨강이면 대비가 아니다.

## 5. 접근성 (Accessibility) — Stage 4

**뜻.** 시각·운동 제약이 있는 사용자도 같은 과업을 끝낼 수 있다. 전 세계 사용자 4명 중 1명 이상이 시각 장애를 경험한다. WCAG 를 기준으로 삼는다.

**적용.**
- 키보드만으로 전부 할 수 있다. 포커스가 보이고, 탭 순서가 읽는 순서다.
- 아이콘만 있는 컨트롤에 접근 가능한 이름을 단다. 이미지에 대체 텍스트를 단다.
- 상태 변화(저장됨·실패·진행 중)는 색 말고 글·아이콘으로도 전달한다.
  - 보조기기에도 알림(live region)으로 전달한다.
- 전경·배경 대비가 충분하다. 애니메이션은 줄이기 설정(`prefers-reduced-motion`)을 따른다.
- 쓸 수 없는 행동은 숨기거나 죽이기보다 **왜 안 되는지 말한다**(`aria-disabled` + 이유).
- 한 글자 단축키는 텍스트 입력 중에 발동하지 않는다.

**점검.** 마우스를 빼고 이 과업을 끝까지 해 봤나. 스크린리더가 이 버튼을 뭐라고 읽나.

**흔한 실패.** 복합 위젯의 `slider`·`option` 역할 안에 상호작용 자식을 넣으면 자식의 이름과 상태가 조용히 사라진다. `disabled` 로 죽인 버튼은 탭 순서에서 빠져 "왜 안 되는지" 물을 기회도 없다.

## 6. 근접성 (Proximity) — Stage 2

**뜻.** 가까이 있는 것은 관련 있어 보인다. 관련 있는 것은 붙이고, 다른 일은 뗀다.

**적용.**
- 한 대상에 대한 컨트롤은 한 묶음으로 둔다(재생·일시정지·다음은 한 줄, 종료는 따로).
- 폼의 라벨은 그 입력에 붙인다. 오류 문구는 그 입력 바로 아래에 둔다.
- 파괴적 행동은 주 행동 묶음 밖에 둔다.

**점검.** 이 컨트롤 옆에 있는 것과 같은 대상을 다루나. 아니라면 왜 옆에 있나.

**흔한 실패.** 툴바에 비슷한 아이콘(✂ 나누기 / ✁ 잘라내기)을 세 칸 거리에 둔다. 사용자는 툴바를 읽지 않고 훑기 때문에 동전 던지기로 고른다.

## 7. 정렬 (Alignment) — Stage 2

**뜻.** 깔끔한 선이 신뢰를 만든다. 그리드가 질서와 예측 가능성을 준다.

**적용.**
- 레포 토큰의 간격 단위만 쓴다. 눈대중 픽셀은 쓰지 않는다.
- 표·일정표의 열은 세로선이 맞는다. 숫자는 오른쪽, 글은 왼쪽에 맞춘다.
- 밴드·칸·격자를 가진 화면은 격자 경계와 시각 경계가 일치한다(30분 격자면 눈금도 30분의 배수).

**점검.** 화면의 세로 기준선이 몇 개인가. 셋을 넘으면 그리드가 없는 것이다.

**흔한 실패.** 격자 단위와 렌더 단위가 달라(10분 눈금 vs 30분 일정) 순서가 뒤바뀌어 보인다. 여백을 비율로 두면 창 크기마다 정렬이 흔들린다. 이것은 고정 px 토큰으로 푼다.

## 프로 팁 4 — 원칙을 넘어서

1. **관점을 정한다** (Stage 0)
   - 사용자 흐름을 먼저 정하고 요소 배치를 거기에 맞춘다.
   - 요소부터 놓고 흐름을 끼워 맞추지 않는다.
2. **간편하게** (Stage 1·3)
   - 화면 사이 탐색이 같은 규칙을 따른다.
   - 모든 행동에 즉각적 시각 피드백이 있다.
   - 흔한 과업에는 지름길이 있다.
3. **지름길** (Stage 1)
   - 지름길은 키보드 단축키·최근 항목·기본값이다.
   - 초심자 흐름을 늘리는 대신 숙련자 경로를 따로 둔다.
   - 단축키는 OS·브라우저가 이미 쓰는 조합을 피한다.
4. **테스트** (Stage 5)
   - 사람이 실제로 쓰는 것을 본다.
   - 그린 테스트 스위트를 통과한 결함이 전부 "사람이 무엇을 겪나"에서 났다.
   - 정기적으로, 초심자와 키보드 사용자의 눈으로 본다.
